# Архитектура content-bot

Полное описание — в `README.md`, инженерные правила — в `docs/practices.md`, принятые решения —
в `docs/decisions.md`. Здесь — то, что нужно применить прямо сейчас, без чтения всего.

## Куда это положить

Вопросы по порядку, останавливайся на первом «да»:

1. **Принимает работу извне** (HTTP, очередь, cron, команда бота)? → `src/app/`
2. **Используется несколькими фичами и это механизм или домен**? → `src/core/`
3. **Продуктовая область, которую можно вырезать целиком**? → `src/modules/<name>/`
4. **Мелкая утилита без знания о домене**? → `src/lib/`
5. **Контракт между слоями или каталог значений**? → `src/types/` или `src/const/`

**Данные кладём к владельцу**: таблица живёт там же, где код, который ей распоряжается.
Двух владельцев у таблицы не бывает.

## Границы (проверяются ESLint, `pnpm check`)

```
index.ts  →  app  ⟂  modules   →  core  →  lib  →  types/const
```

- `app` и `modules` **не видят друг друга** ни в одну сторону
- `modules` не видят друг друга
- `core` не знает ни о фичах, ни о входе; `lib` не знает ни о домене, ни о транспорте
- Связывание — только в `src/index.ts`
- Тип зависимости описывает **потребитель** (порт), а не владелец

## Роли файлов

**Канон обязателен только для `modules/`** — открыв любую фичу, видишь одно и то же:

`index.ts` публичный контракт (код писать можно) · `service.ts` логика · `queries.ts` запросы ·
`table.ts` схема · `schema.ts` zod · `types.ts` типы · `commands.ts` команды бота ·
`sections.ts` разделы фичи · `upstream.ts` свой внешний клиент

Заводи только нужные файлы, но называй всегда так.

⚠️ **`core/` и `app/` канону не подчиняются**: это инфраструктура и вход, полный набор им не нужен.
Хватает одного файла — пусть будет один (`core/telegram.ts`). Есть таблица и логика — появляется
папка (`core/sections/`).

Роль разрослась → папка с тем же именем и `index.ts` внутри.
Папка с одним `index.ts` → сверни обратно в файл.

## Проверь себя перед тем, как положить

- **«Если удалить эту папку, что сломается?»** Отвалится чужой код — лежит не там.
- «Понадобится ли это из очереди или cron, а не только из Telegram?» Да → это не `app`.
- «Это продукт или устройство бота?» Продукт → фича, устройство → `core`/`app`.
- «Сколько владельцев у этих данных?» Больше одного → владение нарушено.

## Как добавить фичу

1. Папка `src/modules/<name>/` с нужными ролями
2. Имена команд — в `src/const/commands.ts` (там же поле `sections`, если команда только для раздела)
3. Связывание в `src/index.ts`: создать сервис, добавить команды и разделы в списки
4. Нужны данные фичи входу — добавь метод в порт, не импорт
5. `pnpm db:generate` при изменении таблиц, затем `pnpm check`

## Чем это подкреплено

Не выдумано — проверено по источникам. Когда правило кажется формальностью, здесь причина.

- **Фаулер, Presentation-Domain-Data Layering.** Слои по типу файла годятся, пока приложение
  маленькое: _«once any of these layers gets too big you should split your top level into domain
  oriented modules which are internally layered»_. Отсюда наш верхний уровень по фичам, а внутри
  фичи — роли.
- **Богард, Vertical Slice Architecture.** _«Minimize coupling between slices, and maximize coupling
  in a slice»_. Отсюда запрет импортов вбок и разрешение писать внутри фичи как удобно.
  ⚠️ Он же предупреждает против обязательных цепочек «контроллер → сервис → репозиторий»:
  наш канон задаёт **имена** ролей, а не требует заводить их все. Тривиальной фиче хватит
  `index.ts` и `service.ts`.
- **Гжибек, Modular Monolith.** Модуль = бизнес-возможность, не слой; общается контрактом;
  прячет внутренности. Отсюда `index.ts` как публичный контракт и порты между фичами.
- **Кокбёрн, Ports & Adapters.** Порт — протокол разговора приложения с внешним миром, адаптер
  переводит. Правило асимметрии: внутреннее не протекает наружу. Отсюда `core/telegram` как адаптер
  и порты, которые описывает потребитель.
- **Фаулер, Bounded Context.** Границы проводит язык, а не таблицы. Если для «материала» в разных
  местах нужны разные модели — это две фичи, а не одна с флагом.
- **Фаулер, CQRS.** _«You should be very cautious about using CQRS… for most systems CQRS adds risky
  complexity»_. У нас лёгкая форма: `queries.ts` отдельно от `service.ts`, и всё. Полный CQRS
  с разными моделями чтения и записи не заводим.
- **Фаулер, Microservice Trade-offs.** _«There is a Microservice Premium»_. Один воркер — осознанный
  выбор; делим, только когда упрёмся в лимиты, а не «чтобы красиво».

## Что делать, если правило не даёт ответа

Не угадывай молча. Опиши развилку, предложи вариант с обоснованием и, если решение принято,
допиши строку в `docs/decisions.md`.

## Типичные ошибки этого проекта

| Симптом                             | Куда на самом деле |
| ----------------------------------- | ------------------ |
| Команда фичи лежит во входе         | к владельцу        |
| Данные одной фичи в общем каталоге  | в свою папку       |
| «Фича», которой пользуются все фичи | в `core/`          |
| Утилита знает про HTTP              | маппинг во вход    |
