# Решения, альтернативы и открытые вопросы

Журнал: почему устроено так, а не иначе. Новое решение дописываем сюда с датой, чтобы не обсуждать
дважды. Детали живут в профильных документах, здесь — суть и причина.

## Журнал решений

Дополнение 19.09.2026 после проверки реализации:

- Разделы — общий механизм `core/sections`; будущие продуктовые определения принадлежат
  `modules/<owner>/sections.ts`. Временный стартовый каталог остаётся рядом с механизмом.
- Текущий бот обслуживает только личный чат владельца. Одна база — один бот и владелец.
- Вход сохраняется с арендой; исходящие операции Telegram — с отдельными стабильными ключами.
  Сеть/таймаут/5xx не доказывают отсутствие эффекта, поэтому неизвестный исход требует сверки.
  Новый брокер, DO и cron для этого локального этапа не добавляем; восстановление — `pnpm recover`.
- Разработка и проверка пока только локально с dev-ботом. Прод-бот — после 2–3 основных разделов.

## Отклонённые альтернативы

**`mtproto-agent` — постоянный процесс вне Cloudflare.** Снял бы лимит в 20 МБ и вернул сценарий
«отправил ролик боту в чат»: MTProto авторизует и ботов (`api_id` + `api_hash` + `bot_token`), юзербот
не нужен. Не берём — второй рантайм, сессия, секреты и мониторинг ради трёх файлов в неделю.
Шов в модуле `media` сохранён: переключение драйвера не трогает остальные модули. Возвращаемся, если
загрузка из Mini App окажется неудобной на практике. Разбор — в `publishing-and-media.md`.

**Локальный Bot API server (`telegram-bot-api`).** Тот же результат, но демон на C++ с диском —
тяжелее MTProto-клиента. Отклонён по той же причине.

**Задеплоенный dev-воркер в ежедневном цикле.** Деплой на каждую правку — минуты ожидания вместо
горячей перезагрузки. Локальная разработка остаётся основным режимом; задеплоенный dev понадобится
на этапе 2, когда появятся cron, очередь и alarm'ы Durable Object, которых локально нет в том же виде.

**Mini App вместо бота.** Mini App — страница внутри Telegram, она не принимает сообщения и
запускается кнопкой из бота. Разговорный сценарий («перепиши начало», «убери тут шутку») в форму
не укладывается. Остаётся точечно под загрузку видео, где веб-страница объективно лучше чата.

**Запуск MTProto внутри Worker.** TCP у Workers есть (`connect()` из `cloudflare:sockets`), но протокол
шифрует весь поток: 250 МБ пришлось бы расшифровать в JS — против лимита 10 мс CPU на Free.

## Почему именно так

1. **`AppError { code, message, retryable }`, а не HTTP-статус.** Потребителей ошибки два — Telegram и
   очередь, и решение о повторе важнее кода ответа.
2. **Без `@hono/zod-openapi` и Swagger.** У одного webhook нет потребителя схемы; валидация остаётся
   на чистом zod. Вернёмся к OpenAPI вместе с API для Mini App.
3. **D1 как основное хранилище, а не KV.** Нужны транзакционные статусы, версии и локи; KV
   распространяет изменения с задержкой и для этого не годится.
4. **Durable Object для расписания и локов.** Alarm'ы дают таймеры и сериализацию изменений одного
   материала без «cron раз в минуту + самодельный лок»; на Free доступен с SQLite-бэкендом.
5. **`core/jobs` с двумя драйверами** (очередь / добор из D1) — следствие бесплатного тарифа:
   Queues Free даёт 10 000 операций в день и хранит сообщения 24 часа, поэтому источник истины — D1.

## Открытые вопросы

Пока не решены — интерфейсы проектируем так, чтобы поставщика можно было заменить:
модель ИИ и источник актуальных данных; названия рубрик и их правила; допустимый способ подключения
TikTok; условия подписки R2; часовой пояс; канал и аккаунты.
