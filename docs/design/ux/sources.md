# §3.9 Источники и разбор события

## 3.9 Источники и разбор события `/sources`
- **Purpose:** inspect persisted health and official Dota updates; open one read-only detail for a stored update and its deterministic patch facts; manage exact hero/item watches and inspect their confirmed matches; compare bounded recent-match hero observations from the separately labelled community source OpenDota. No feed refresh, parser trigger, draft creation, edit, approval or publishing from this page.
- **Tabs:** «Обновления», «Источники», «Герои». The first two keep their current behavior and the two configured official feed summaries. «Герои» reads only the latest two persisted snapshots; it does not trigger an upstream fetch.
- **Hero statistics:** identify OpenDota as a community source (not Valve), show last successful observation and current health, and provide a bracket selector (1–8) or «Профессиональные». Show hero, wins, picks/sample count and win rate only when picks are positive; show professional bans as a raw count only. Movers compare win-rate percentage points between the latest two observations, require at least 100 picks in both, and are labelled as a difference between observations—not as a 6-hour/24-hour trend or patch effect. Unknown counts stay unavailable, not zero.
- **Hero statistics states:** no successful poll = source attribution plus an explicit unverified state; one snapshot = current statistics plus «Недостаточно данных для сравнения»; latest observation older than 24 hours = stale warning; last poll failed = degraded warning while retaining the last good snapshot; no qualifying movers = explain the sample floor. Network/5xx/401/403 handling follows the shared safe-read behavior. No manual refresh or mutation action is shown.
- **List:** retain the two configured official source summaries and bounded newest-first update list. Every persisted update adds a separately named «Открыть разбор: {title}» link; patch details show stored parse outcomes and Steam details show `not_applicable`. Source and existing-draft links remain distinct. Filters/search stay mounted while detail is open.
- **Detail address:** `?update={sourceKey}:{externalId}`. It displays the observed title, source identity, published/detected timestamps in the owner timezone, explicit parse outcome, confirmed facts (entity, known section/category, parser-provided change; direction and before/after only when supplied), and exactly one canonical source link at update level. No per-fact source links until source-location data exists. Show the existing draft link only when the update already has one.
- **Detail layout:** one visible «← К обновлениям» link, descriptive focused heading, metadata, parse status/caveat, then fact cards in reading order and actions. At phone widths, stack the same information in that order. No horizontal page scroll down to 320 px.
- **Parse states:** `complete` shows confirmed facts with a caveat that they are not exhaustive; `incomplete` says «Требует ручной проверки» and shows only independently confirmed facts; `no_recognized_facts` explicitly says no facts were confirmed and does not claim the source has no changes; `pending`, `not_applicable` and `unavailable` are distinct from empty results. The API contract defines the enum and payload.
- **Read/error states:** loading uses detail-shaped skeleton with `aria-busy`; network/5xx shows concise error and `requestId` when present with safe GET retry; `404` gives a safe missing-update message; final `401` after the standard silent reauth redirects to login and clears private Dota query data; `403` shows no private source/event/fact data. Retry never starts upstream work.
- **Navigation/focus:** opening a detail focuses its heading after data/error resolves; browser Back/Forward is URL-addressable. The back link removes only `update`, preserving other search state, and restores focus to the exact opener; a deep link has no opener and focuses its detail heading. Invalid query values show a safe missing-update view.
- **Responsive/accessibility:** list follows the shared table/card pattern; detail stays in content order at all widths. Every link has a meaningful name, status is never colour-only, keyboard activation works, and focus is visible. Full viewport matrix and axe/keyboard evidence are recorded by the UI QA gate.
- **Watchlists (additive, only confirmed entities):** keep the accepted «Обновления / Источники» behavior and add the «Герои» tab separately. In «Обновления», place a «Мои отслеживания» panel after the existing filters and before the bounded update list; official source health remains in «Источники» and hero statistics remain in «Герои». Show each active exact hero/item as a named row, kind label, enabled status, latest confirmed matching update (or «Совпадений пока нет») and the alert outcome only when the existing alert record proves it. Add from an eligible confirmed hero/item fact with «Следить за героем: {name}» / «Следить за предметом: {name}». A fact individually returned as confirmed remains eligible even when its update parse state is `incomplete`; do not offer add for unresolved, unsupported, or merely mentioned entities. The same entity is shown as already watched and cannot be added twice. Remove with a row action «Не отслеживать: {name}»; request confirmation is unnecessary because it is private and reversible. Show success only after server confirmation; an undo affordance may call the opposite operation only if the API guarantees that operation, otherwise keep the explicit row action available. Exact wording/action availability must follow the returned DTO status.
- **Confirmed matches:** matched facts remain part of the bounded official update feed, with a «Совпадение» label and the matched watch entity; no separate synthetic event or inferred match. A notification state of confirmed sent is «Уведомление отправлено»; definite failure is «Уведомление не отправлено» with its existing incident link if present; ambiguous delivery is «Требует проверки» with «Telegram мог получить уведомление. Повторная отправка отключена, чтобы не создать дубль.» Never show a retry/resend control for an ambiguous outcome. Missing or unprovable delivery state is «Статус уведомления неизвестен», not sent.
- **Watchlist responsive behavior:** desktop uses the shared Panel row/table anatomy; under 860 px each watch and match becomes a stacked row card in the same panel. Put remove in that watch's «⋯» menu, not behind hover. Keep the add action on the fact card. Touch targets are at least 44 px; no horizontal scrolling. In Mini App, the same actions remain available and Telegram BackButton is the exit.
- **Watchlist focus and recovery:** add/remove submits disable only the affected action; focus stays on its control while pending. After confirmed add, focus the new watch row; after confirmed removal, focus the next row or the panel heading if it was last. A 409 preserves the attempted choice, announces the conflict and reloads current server state; the owner explicitly chooses again. Failed mutation keeps the watch and provides a persistent retry-safe message/request ID. Do not optimistically flip status. Unknown alert outcome remains visible in the match row and can be left freely; opening its incident is a separate link and never triggers resend.
- **API needs:** owner-only bounded watch list and match data; supported-entity eligibility tied to confirmed persisted patch facts; idempotent add/remove operations and conflict/version behavior; per-watch last matched update; per watch-update alert state that distinguishes sent, definite failure and ambiguous/unknown; a safe incident link where available. Hero statistics use a separate cached read contract; it does not change the two-feed update list or allow upstream fetch from the page. The page must omit add/remove or delivery claims until these fields/operations exist. No cosmetics or inferred matches.
