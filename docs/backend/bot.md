# §5 Owner notice on schedule, bot as the entry point

## Owner notice on schedule (as built)

After a publication is created for a future time, or rescheduled to one, the bot sends the owner's private chat (`chat_id` = the session's Telegram ID) one message: post title (the first words of the text if it has none), channel, and the time in the zone the owner scheduled in (`publications.timezone`; the settings module stores no zone), with a `web_app` button «Подробнее» to `<origin>/publications?id=<publicationId>`. If the selected revision has media, the first attachment is sent with that notice as one media message; otherwise it is a text message. The text/caption is Telegram HTML with every user-controlled part escaped. `publishing` owns the port `ScheduleNotifier` (`application/ports.ts`); the use cases call it only after the guarded D1 write applied, so an idempotent replay, a refused request, a send-now publication (status `queued`) or a move to "now" announce nothing. The adapter `app/notifications/create-schedule-notifier.ts` is wired in `publications-routes.ts` and runs in `ctx.waitUntil` with no retry; the Telegram send call has a 5 s deadline (the two D1 reads before it do not). It is best effort: any failure, or a missing `TELEGRAM_BOT_TOKEN`, ends as a log line (`component: owner_notice`, stable `errorCode`, no text, token or payload; a Telegram failure also adds the shared `component: telegram` line), never as a changed response. It is not the publishing transport and never reads or writes jobs. Its two reads (revision snapshot, destination) count toward the per-invocation D1 budget (pinned in `query-budget.test.ts`).

**Look (14.10.2026).** Every owner message uses one template (`app/notifications/notice-template.ts`): an icon and bold status line, the post title in bold, then facts with icons (📣 channel, 🕒 time «18 октября, 13:45 (Europe/Chisinau)», 💬 reason), and an optional italic note on what to do. Statuses: 🗓 запланирована, 🔁 перенесена, ✅ опубликовано / снова работает, ❌ не отправлена, ⚠️ не подтверждена / источник Dota не обновился, 🔂 повторилось N раз (with the first time in the owner's zone, not UTC). Dota source alerts give a Russian reason instead of the code and open `/sources`.

**«Опубликовано» (14.10.2026).** After a Cron tick stored its outcomes, the owner gets ✅ «Опубликовано» for each send whose `succeeded` write applied (`DispatchSummary.delivered`, filled next to `raised`), at most 3 per tick, 5 s deadline, no retry: buttons «Открыть в Telegram» (`t.me/<username>/<id>` or `t.me/c/<id>/<id>`) and «Подробнее». It follows the «Опубликовано» switch (`sentNotices`). «Запланирована», «Перенесена» and «Отменена» (🚫, sent after the owner's own cancel applied) follow «Планирование» (`scheduleNotices`); both default to on, also for a settings document saved before 14.10.2026. The app origin and the settings are read once per tick and shared with the incident alerts.

## Bot as the entry point (as built, plan step 1a)

**Webhook.** `app/bot/webhook-route.ts` checks the secret header in constant time, loads the bot identity and builds a grammY `Bot` per request. The middleware chain is: failure catch (the webhook always answers 200 once past the secret, so Telegram never redelivers an update whose reply may be out), owner check (`from.id === OWNER_TELEGRAM_ID`; everyone else is dropped silently and their update id is not stored), private chats only, then dedup. **Dedup:** `webhook_updates.update_id` is a PRIMARY KEY; `INSERT ... ON CONFLICT DO NOTHING` and `changes === 1` means first sight, a replay ends without a reply. The same batch deletes at most 5 rows older than 3 days, so the table needs no Cron step. A claimed update whose handler then fails is not retried (the owner sends it again); a crash between claim and reply loses that one update, which is preferred to a second draft.

**Owner commands.** The menu is `/start`, `/redactor`, `/post`, `/analytics`, `/stop` (`OWNER_COMMANDS` in `app/bot/owner-chat.ts`), registered with `setMyCommands` for the owner's chat on `/start` and on connect; the owner presses `/start` once after a deploy that changes the list. A failed read is answered with «Не удалось получить данные. Попробуйте ещё раз.» and logged with a stable code.
- `/start`: «Студия на связи. Откройте её кнопкой ниже.», button «Открыть студию» → `<origin>/`. In the background it stores the origin (below) and refreshes the commands and the menu button (it shows the command list; the studio opens from this reply).
- `/redactor` and `/post`: the AI writer and the drafts mode, below.
- `/analytics` (AI plan P6): the daily report's numbers at this moment with their `as_of`, without the AI review (no model call); stored nowhere, so it never replaces or repeats the daily report.
- `/stop` (owner, 19.10.2026: the «Закончить» button scrolls away): ends the /redactor or /post mode and every wait of the chat — a facts answer, the owner's version, a note, a publication time — and answers «Готово, режим закончен.».
- `/rule <текст>` and `/rules` (not in the menu, AI plan P7; answer when typed, also inside /redactor): `/rule` with 3–300 characters asks «Для каких текстов?» with «Все тексты», «Учусь играть», «Учу фидить», «Посты», «Рилсы вне рубрик», «Отмена» (`rl:<id>:<a|i|f|t|s|x>`); a tap makes the rule active once (a second tap: «Эта кнопка устарела.»), otherwise the usage example. At most 15 rules are in use at once (a 16th scope tap answers «Уже 15 правил…»; a scope never picked is dropped after a day). `/rules` lists them, each cut to 180 characters, with «Отключить N» (`rl:<id>:off`); an off rule leaves the next prompts, old texts stay. A style lesson from the owner's edits (`docs/ai/architecture.md` item 10) is asked once by content alert «✍️ Похоже, вы всегда так правите в …» (or «Понял из вашего замечания» for a remark) with «✅ Учитывать» (`sp:<id>:ok`: an active owner rule of that format, listed in /rules; a double tap makes one rule; at the 15-rule cap the lesson waits and the same button works later) and «Нет» (`sp:<id>:no`: never proposed again). An analysis rule (`docs/ai/architecture.md` item 10) is asked once by content alert «💡 Похоже, работает в …» with «✅ Учитывать» (`rl:<id>:ok`: in use, «из аналитики» in /rules) and «Нет» (`rl:<id>:no`: disabled, never proposed again); a tap on a rule that is no longer supported or already answered gets «Эта кнопка устарела.». Rules live in `ai_rules` (migration 0079); the writer gets every in-use rule of the draft's format and «Все тексты».
- `/status` (not in the menu, owner 18.10.2026; answers when typed): «Публикация: включена | выключена | включена, но не задан токен бота», «Cron: последний запуск N мин назад, без ошибок | с ошибкой (давно: проверьте Cron when older than 3 min) | нет данных о запусках», «Проблемы: неизвестно N, не отправлено N, открытых инцидентов N | проблем нет». Counts stop at 5, 5 and 20 (shown as `5+`); button «Разобраться» → `<origin>/publications?status=unknown` (else `failed`) when there is a problem, otherwise «Открыть студию» → `<origin>/`. It reads `PublicationRepository.list`, `DispatchRepository.countOpenIncidents` (bounded count over `incidents_open_idx`) and the system state: about 4 statements, every SELECT with a LIMIT or by primary key (pinned in `bot-entry-point.test.ts`).

**Drafts** (owner, 16.10.2026: only in /post mode). `/post` opens the mode with a «Закончить» button (migration 0057; one mode per chat, replacing /redactor; it ends on «Закончить» or after 30 min without a message). In it any text from the owner (typed or forwarded; an unknown `/command` is ignored) and any photo, video or GIF becomes a draft; outside /post and /redactor the bot answers «Чтобы сделать пост — /post, чтобы написать с ИИ — /redactor.» (an album once) and makes nothing. A draft becomes a draft through `createPost` with the idempotency key `tg-update-<update_id>`. Telegram formatting is carried over: `entities` (bold, italic, underline, strikethrough, spoiler, code, pre, blockquote, text links) are shifted to the body by original UTF-16 offsets; the part inside the title, unsupported types (mentions, hashtags, bare links, custom emoji) and formatting the contract refuses are dropped (the text stays). The first line becomes the title; the rest is the body; a first line over 200 UTF-16 units is cut at the limit (never inside an emoji) with «…» and its remainder starts the body, so nothing is lost. A body over 4096 UTF-16 units, or a control character, is refused with a reply and no draft. Reply: «Черновик создан», the publish buttons and «Открыть в Студии» → `<origin>/posts/<id>` (the post editor, not its publish screen; the import report of files too). A poll (typed or forwarded) becomes a poll draft in /post mode (owner, 20.10.2026): its question, options and multiple answers; a quiz keeps its answer and explanation only when Telegram gives exactly one right answer (it does in the private chat with the bot), otherwise it becomes a regular poll; a question over 300 or an option over 100 characters, or options past 12, are cut, not refused. Reply «Черновик-опрос создан» with the same buttons. Any other message type (sticker, voice, document…) gets «Этот тип сообщения пока не превращается в черновик» and no draft.

**Media drafts.** A photo, video or GIF (`animation`) with a caption makes one draft: the caption is title/body with `caption_entities`; without a caption the title is «Медиа из Telegram». The webhook does only fast D1 work: it creates the draft (`createPost`, key `tg-update-<update_id>`; an album uses the fixed key `tg-album-<media_group_id>`, so all its updates share one draft, and one that meets the first still writing waits 300 ms, at most 6 tries), stores one row per file in `bot_media_import_files` (migration 0034: file id, `file_unique_id` UNIQUE per draft, declared size, kind, `message_id` order, status `pending|done|failed`, attempts), and replies «Черновик создан, файлы загружаются…» once per draft (an album: only the update that created its `bot_media_imports` record answers). A file over its limit (the contract's per-kind maximum, capped at 20 MB, the Bot API download limit) is stored as `failed/too_large` and never downloaded. An album caption is stored on the record (the first one wins) and applied by the worker, so no update races on the post revision; the worker reads it again right before the report, and the report is not claimed while a stored caption is unapplied. A caption over 4096 characters is never cut and never drops the file: the draft is made without it (`caption_too_long`), and the one import report adds «Подпись длиннее 4096 символов, она не сохранена.», so there is no separate «too long» answer. `webhookCallback` has `timeoutMilliseconds: 8000` (grammY's default is 10 s, Telegram's own deadline); the handler normally ends in well under a second.

The import worker (`media-import-worker.ts`, wired in `media-import-runner.ts`) runs after the response through `executionCtx.waitUntil` (budget 25 s; an album first waits 1.5 s so its files attach in `message_id` order) and from the Cron tick (step 7b, idle ticks only, at most 2 drafts, 20 s) for leftovers. One conditional `UPDATE` takes a 60 s lease per draft, so only one worker imports a draft at a time; files go one by one, and only one file download runs at a time across the whole Worker (a one-row D1 lease, `bot_media_download_lease`, 45 s; a draft that meets it busy keeps its file `pending`, pauses 5 s and is finished by Cron), so isolates never hold several files at once: `getFile` plus the download share one deadline (20 s or what the budget leaves; bytes kept in memory as one buffer, at most 20 MB), then `uploadPostMedia` (R2, signature and size checks, key `tg-import-<file row id>`) with the revision read right before. A stale revision re-reads and retries the attach only, never the download. A transient failure (Telegram or storage down) pauses the draft for 30 s (order matters) and Cron retries; after 3 tries the file is `failed`. When no file is pending, one conditional `UPDATE` claims the report and the owner gets one message (with the Studio button; without it, text only, when Cron has no stored app origin; a refused send reopens the claim, at most 3 sends per draft): «Файлы загружены в черновик: N.» or the files that failed (too big / could not be loaded). A file arriving after the report reopens it. **Allowance per invocation:** the Free plan allows 50 subrequests, and every statement of a batch counts, so `createContainer` wraps D1 with `platform/d1-budget.ts` (`container.queryBudget`: statements plus the 3 external calls charged per file and 1 per report send). The worker starts a file only when 27 are left (25 for the file's worst case, 2 to free the lease), and sends the report only when 18 are left; otherwise rows stay `pending` (the lease is freed at once) and the next Cron tick carries on in order, so a webhook invocation usually attaches one file and its report comes with the next tick, and a long album takes about one tick per file (`tests/integration/bot-import-budget.test.ts` meters albums of 1, 3 and 10 per invocation). A file's `settle` and its download-lease release are one batch. Service messages (for example `write_access_allowed`) get no reply; only stickers, voice, documents and similar get the unsupported text.

**Owner alerts.** When a tick writes an incident (`publish_failed` or `publish_unknown`, from the dispatcher or reconcile), `DispatchSummary.raised` / `ReconcileSummary.raised` return it after the guarded D1 batch applied. Step 6 of the tick (`alertOwnerOfIncidents`, `app/notifications/`) reads the stored origin, claims all incidents with one `UPDATE incidents SET owner_notified_at = ? WHERE id IN (...) AND owner_notified_at IS NULL RETURNING id`, then sends one message per claimed incident (5 s deadline, no retry, in parallel). The claim comes first, so an incident is alerted at most once however many ticks overlap, and a failed alert is not repeated. A failure (Telegram, D1, no bot token, no owner id, origin not known yet) is one log line `component: owner_alert` with a stable `errorCode` (`BOT_TOKEN_MISSING`, `OWNER_ID_MISSING`, `APP_ORIGIN_UNKNOWN`, `ALERT_STATE_UNAVAILABLE`, `UNAVAILABLE`, `RATE_LIMIT`) and never changes job state; the alert writes no incident of its own, so there is no recursion: if the Telegram error notification itself fails, the incident is already saved in D1. A tick without incidents spends nothing. Incidents that existed before migration 0009 are marked notified. There is no periodic check of channel rights: loss of rights is seen only as a send that fails with `DESTINATION_UNAVAILABLE`, whose alert says so. Templates: failed «Публикация не отправлена / Пост / Канал / Причина»; unknown «Отправка не подтверждена / Пост / Канал / Сообщение могло выйти в канал. Проверьте канал вручную: бот не отправит его повторно сам.»; button «Открыть» → `<origin>/publications?id=<id>` (without a publication: `<origin>/publications?status=failed|unknown`). Post and channel lines appear when the dispatcher had them in hand (reconcile has none).

**System state (`system_state`, migration 0009).** `cron_last_run` is one upsert at the end of every tick (also a failed one); it is why an idle tick now costs 3 reads and 1 write. `app_origin` is stored by `/start` and by connect, because Cron has no request to learn the Worker's public origin from; alerts are skipped (`APP_ORIGIN_UNKNOWN`) until one of them ran. A deployment before the migration logs `heartbeat` / `ALERT_STATE_UNAVAILABLE` and keeps ticking.

**Owner instructions: webhook registration and its status.** Secrets are set by the owner: `TELEGRAM_BOT_TOKEN` and `TELEGRAM_WEBHOOK_SECRET` (1-256 characters of `A-Za-z0-9_-`). Apply migration 0009 to the environment's D1 first. Then press «Подключить бота» on Обзор (system status): the Worker calls `getMe`, `setWebhook` (`<origin>/webhooks/telegram`, the secret as `secret_token`, `allowed_updates: message, callback_query, chat_member`; a bot connected before 20.10.2026 must be connected again once for the invite link counts), clears stale command lists, sets the owner's commands and menu button and stores the origin. Status (`GET /api/v1/bot/status`, shown in the system status) reads `getWebhookInfo`: the expected URL, `pointsHere`, `pendingUpdateCount`, `lastErrorAt` and message. Without the UI: `curl "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"` (do not paste the token anywhere shared) and, to register by hand, `curl -F url=<origin>/webhooks/telegram -F secret_token=<SECRET> -F 'allowed_updates=["message","callback_query","chat_member"]' "https://api.telegram.org/bot<TOKEN>/setWebhook"`. Then send `/start` to the bot.

## Publish buttons under draft replies (as built)

The draft reply (text path and the media import report) carries one inline button «Опубликовать сейчас → <channel>» per enabled destination, at most 3 (only for a post that still is a draft with files) (with more, or none: only the Studio button), then «Открыть в Студии» (`web_app` to `<origin>/posts/<id>/publish`; omitted when Cron does not know the origin). `callback_data` is `pub:<token>`, a 20-hex token naming a row of `bot_publish_actions` (migration 0035: post, destination, the draft revision the owner saw, status `pending|claimed|done|stale`, `publication_id`, `created_at`, `used_at`); the reply «Черновик создан, файлы загружаются…» carries only the Studio button; publish buttons appear on the text-draft reply and on the import report, after every file settled. `UNIQUE (post_id, post_revision, destination_id)`: a re-sent report reuses the existing token (a refused or still-pending one is re-armed), never mints a second. Rows older than 24 h are purged by the hourly idle cleanup step (bounded by `CLEANUP_LIMIT`).

**«🕒 Запланировать → <channel>»** (owner, 17.10.2026; migration 0069) sits under each «Опубликовать сейчас»: `sch:<token>` swaps the buttons for «Через 1 час», «Сегодня 19:00» (while it is ahead), «Завтра 10:00», «Своё время» and «← Назад». A choice publishes through the same token and use case at that instant (`bot_publish_actions.scheduled_at`, fixed by the claiming tap), so the same refusals and the duplicate guard apply; the answer is «Запланировано: <channel>, завтра в 10:00» in the owner zone. «Своё время» waits up to 10 minutes (`awaiting_time_until`) for the next text, read by `schedule-time.ts` in the owner zone: «завтра в 2 дня», «в 7 вечера», «через 2 часа», «в пятницу в 10», «20.10 18:00», «20 октября в 15»; a time without a day that has passed means tomorrow; an unreadable, past or more than 366 days ahead time is asked again before anything is claimed; «Отмена» ends the wait. Only a short one-line text (up to 40 characters) is taken as the time: a longer text ends the wait and goes on as usual (a post that says «стрим в 20:00» never schedules the earlier draft), and a reply or a command is never the time. «Своё время» and «✏️ Изменить» end each other's wait. After «Поставлено в очередь» or «Уже в очереди» the message keeps one button, «Открыть в Публикациях» (`/publications?post=<post>&id=<publication>`: this very publication open), owner 17.10.2026: the publish screen invited a second publication); other answers open the post. A second publication of a post to a channel while one is on its way is refused by the server too (`ALREADY_PUBLISHED`). A tap passes the same gates as a message (owner, private chat, `update_id` dedup), answers `answerCallbackQuery` first, then `app/bot/publish-actions.ts` runs: expiry (24 h after `created_at`, only while `pending`) -> conditional claim `pending -> claimed` (fixes `used_at` as the send-now instant, so every tap of the action builds an identical request) -> approve the draft at the stored revision (a conflict is re-read; approved at that revision by someone else also continues) -> `createPublication` (the HTTP API's use case) with `Idempotency-Key: tg-pub-<post>-<revision>-<destination>` (shared by every token of that revision and channel) -> `claimed -> done`. Repeated, redelivered and concurrent taps therefore return the one publication (`IN_FLIGHT` is answered silently). The bot never sends: the dispatcher does.

A tap while the post still has an open media import (files pending or the report not out) creates nothing, is checked before the action is claimed (so `used_at` is not fixed and the button stays alive past the 5-minute schedule window) and is not final: the message becomes «Файлы ещё загружаются — дождитесь отчёта или откройте в Студии», and the button works after the report. A post that already has a publication to that channel in any status except `failed` or `cancelled` is refused (token `stale`): «Уже в очереди или опубликовано в этом канале — откройте в Студии». A changed post (revision, archived, empty body, destination disabled or gone) ends `stale` for good and the message becomes «Пост изменился — откройте в Студии»; an expired or unknown token gives «Кнопка устарела, откройте в Студии». Success edits the message to the server's status label («Поставлено в очередь: <channel>» for `queued|scheduled`); the word «Опубликовано» is never used by the bot.

## Contamination confirmation under analytics alerts (as built, migration 0066)

The TikTok alerts «Ролик перестал набирать» and «Ролик пропал из TikTok» carry «Ограничение подтвердилось» / «Удаление подтвердилось» (`callback_data` `cc:r:<itemId>` / `cc:d:<itemId>`, written by `modules/content-analytics/contamination-callback.ts`; an item id that would not fit 64 bytes gets no button). Only the owner's tap marks the video contaminated (reason `restricted` / `removed`, the same record as the item panel's «Искажение данных»), so it leaves every usual curve; the alert alone never does. The tap passes the same gates as a message, is safe to repeat, answers with a toast and removes the button from the message; an unknown item or a malformed button marks nothing.

## AI writer in the owner's chat (as built, migration 0054)

- **Request.** One command, `/redactor` (owner, 16.10.2026; second in the menu after /start) opens a chat with the editor. Its first message has buttons «Пост в ТГ», «Учу фидить», «Учусь играть» (no plain Reel): a tap makes the next message a draft of that format, a second tap clears it, and the chat is free again after that message. Otherwise every text in the chat goes to the AI until «Закончить» or 30 min of silence (migration 0055; the last 8 turns are kept, migration 0056, and sent with each message). Words after the command are the first message. The editor answers in the author's voice and knows what it can do; a message that asks for a post or Reel in words («придумай рилс …», «напиши пост в тг …») becomes a draft of that format, and so does a message that opens with a rubric name («Учусь играть на Пудже», «Учу фидить …»). Outside any mode, the same wording also makes an AI draft; any other text gets the hint above.
- **Writing.** The bot answers «Пишу…» at once and sends the model call to Queue `AI_JOBS` (owner, 19.10.2026: the default reasoning effort ran past the 30 s a webhook's `waitUntil` has; quality is not traded for speed). The consumer (`app/ai-queue.ts`, 15 min of wall time) claims the job id once in D1 (migration 0074; a redelivered message does nothing), gives the model 120 s at its default effort (a claim is per job, not per answer: if the queue accepted a job but reported a failure, or delivered it after the 5-minute lease and the owner tapped retry, one answer can cost two model calls; nothing is published twice), then edits that message into the hooks, the text, the code-check findings and the buttons. AI off, no key, no priced model or a spent budget is said in the same message; budget alerts follow in the chat.
- **Buttons** (`ai:<generationId>:<action>`): «Хук N» puts that hook at the start (still AI text), «Ещё вариант» / «Короче» / «Смешнее» write a new version as a new message, «Что не так?» swaps the buttons for the reasons (Тема повторяется, Слабый хук, Шутка не зашла, Не мой стиль, Слишком длинно, Ошибка в фактах, Не то задание, «← Назад»; `r:<reason>`): a tap stores the reason once per draft with the revision on screen (migration 0067), answers «Записал: …» and brings the draft's buttons back; a reason is only recorded, never a style rule by itself. The `joke` action of older messages still records «Шутка не зашла». «Одобрить» approves. After a reason the bot asks for a note: the next plain message (not a command, not a reply) is stored as the verdict's note (≤ 500, migration 0071, `ai_writer_requests.noting_feedback_id`); «Без пояснения» (`ai:nonote`) ends the wait. **Fix by the remark** (plan P2, 19.10.2026): «Что не так?» also makes the chat wait for the owner's own words (migration 0075, `fixing_generation_id`; claimed once, «← Назад» ends it). That message, or the note after a reason, is the remark: job `fix` rewrites the current version changing only what the remark names (structured output `writer_fix` adds `changes` and `reasons`), shows «Что изменил: …» and «↩ Вернуть прошлый» (`undo`: the parent version again as the newest message, nothing deleted). A remark without a reason button is recorded with the first reason the model named; a remark is only recorded, never a rule. «Без пояснения» still only records the reason, with no model call. «Принять» and «Ещё поправить» of the plan are «Одобрить» and «Что не так?» on the fixed version. An awaited time or edit is read first; the last wait started wins.
- **Owner edit.** «✏️ Изменить» under a draft (owner, 17.10.2026: replying to a message is awkward) sends the current text to copy and makes the chat wait for the owner's version (migration 0068 `ai_writer_requests.editing_generation_id`): the next plain message, whatever the chat's mode, is stored as `OWNER_EDITED`, once; «Отмена» stops waiting. A question of the model («нужны ваши детали») makes the chat wait the same way, so the next message answers it. Migration 0073 stores the owner's facts before the model call; the draft from that answer (and any rewrite) uses a structured output that allows only a draft, so one task gets one question; one conditional D1 claim accepts the first answer. On model failure a button retries explicitly from those saved facts. A reply to a draft message still works as an edit. The cancel buttons carry the exact edit or feedback ID, so an old button cannot cancel a newer wait. An approved revision cannot receive another edit; approval rereads the latest text if it changed during the save.
Hook, rewrite, and feedback buttons include a 12-hex suffix of the revision they show; an older button (including legacy `joke` without a suffix) cannot act on a newer owner edit. A hook replaces only an exact known model hook; otherwise it precedes the untouched first line and refuses a result beyond the text limit. A rewrite prompt includes the original task and confirmed owner facts as well as the current text. Long Telegram previews preserve UTF-16 surrogate pairs and leave the full draft in D1; the Bot API's 4096-character limit is counted after HTML entity parsing. A failed draft names its reason and stored code (`AI_TIMEOUT` is the 25 s model timeout, told apart from `AI_PROVIDER_UNREACHABLE`); an approval says the AI learns only when the owner changed the text. A facts answer saved in D1 can be retried explicitly after a failed model call or after a 5-minute processing lease if the Worker stopped (model timeout 120 seconds). If the draft is already ready but Telegram delivery failed, the same retry button shows the existing saved draft without another model call. Replying to the original question again exposes the recovery button when the first placeholder was not delivered.
- **Approval** stores `OWNER_APPROVED` with the edit ratio, once per draft. A Telegram text then becomes a studio draft (idempotency key `ai:<revisionId>`) built only from the approved revision, with the usual publish buttons. A Reels text is stored; Reels are published outside the studio.
- **In the studio:** every draft with its versions, texts and verdicts is in Настройки → ИИ → «История черновиков» (`GET /api/v1/ai/drafts`).
- **Not built yet:** pre-approval with a publish time (`docs/DECISIONS.md` 16.10.2026), the cheap-model intent parser.

**Channel joins (invite links, plan B1).** A `chat_member` update (someone joined or left a chat the bot administers) is handled before the owner check: it is claimed in `webhook_updates` like any update, recorded only when the chat is `ANALYTICS_TELEGRAM_CHANNEL` and the person is not a bot, and never answered. A join stores the subscriber's id, the studio link it came through (matched by URL; none for the public @username) and the time; a leave closes that person's open join. The bot must be an admin of the channel with the right to invite users, or creating a link answers `BOT_CANNOT_INVITE`.
