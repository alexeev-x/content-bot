# §5 The Cron tick as built

## The Cron tick as built (stage 4a)

`scheduled` → `app/scheduled.ts`, once a minute (`"* * * * *"`, UTC). Steps run in this order and each is isolated: a failing step is logged with a stable `errorCode`, the later ones still run, and the tick ends with an error so the Cron invocation shows as failed.

1. **Reconcile** (always, even with the kill switch off). One read through `jobs_claimed_lease` (`status = 'claimed' AND lease_until < now`, 1 row per tick), then one guarded batch for them. Without `send_started_at`: `retry_wait` with `run_at = now + backoff + jitter`, or `failed` / `RETRIES_EXHAUSTED` + incident once the attempts are used up (a Worker that keeps dying cannot loop for ever). With `send_started_at`: `unknown` + incident `SEND_UNCONFIRMED`. Each attempt that has no row gets one (`outcome` `lease_expired` or `unknown`; its `started_at` is the job's last write, so approximate). Every statement is guarded by the same conditions as the job update (`status = 'claimed'`, the same `attempts`, the lease expired, the same send-mark state): a dispatcher that finishes between the read and the write wins and reconcile writes nothing.
2. **Dispatch** (only when `PUBLISHING_ENABLED` is exactly `"true"` and `TELEGRAM_BOT_TOKEN` is set; a missing or whitespace-only token logs `BOT_TOKEN_MISSING` every tick and claims nothing). One due scan for up to **3** jobs, then each job to the end before the next one:
   - the due scan repeats the `jobs_due` predicate literally in two branches (`pending`, `retry_wait`), each `ORDER BY run_at, id LIMIT n`, merged oldest-first. A single `IN` with one `ORDER BY` would read every due row to sort it; this reads at most 2 x n whatever the backlog;
   - conditional claim (SQL above, lease 2 min, `changes === 1`); `RETURNING` gives the attempt number that guards every later write;
   - load the publication's destination (`publications JOIN destinations`) and the post revision snapshot `post_revisions (post_id, revision)` at `publications.post_revision`, through the consumer-owned `PostRevisionSource` port wired in `container.ts` to the content module;
   - refusals before any send: destination disabled → `failed` `DESTINATION_DISABLED`; revision missing, empty text without media, text over 4096, media caption over 1024, unsupported album composition, or stored entities that no longer fit (`validatePostEntities`) → a visible failed state. Posts with media use caption length ≤1024; 2–10 photo/video assets may be one media group; animation is only allowed alone. No text is truncated or split. Every refusal writes the attempt row (`outcome = 'skipped'`), incident, `publications.last_error_code` and audit row in one guarded batch and never calls Telegram;
   - `send_started_at` in its own statement, `WHERE status = 'claimed' AND send_started_at IS NULL AND attempts = ? AND lease_until >= now + 15 s`. The last condition makes the lease outlive the call (timeout 10 s) and the outcome write; if it is not met (or `changes !== 1`) nothing is sent and reconcile recovers the job. Only a confirmed mark allows the call;
   - one `PublicationTransport.send` (grammY `Api` without auto-retry, `AbortSignal.timeout(10 s)`), never throws: an unexpected throw is also `unknown`;
   - one guarded batch for the outcome (attempt row, incident, publication, audit, then the job update last), guarded by `status = 'claimed'` and the same attempt; if the first write throws, the job and its attempt row are re-read: a write that committed and lost its response counts as applied, otherwise it is repeated once (guarded, so a repeat cannot duplicate). One such retry is allowed per tick; the next failing write ends the tick (the job is recovered by reconcile). If a write is not applied, reconcile resolved the job first and its state stands.

   | Outcome | job | attempt `outcome` / `error_code` | incident |
   |---|---|---|---|
   | sent | `succeeded`, `publications.external_message_id` (first) and `external_message_ids` (all) | `sent` | no |
   | 429 | `retry_wait`, `run_at = now + max(retry_after, backoff) + jitter (0-5 s)`, `send_started_at` cleared | `rate_limited` / `RATE_LIMITED` | no |
   | 429 on attempt 5 (`MAX_ATTEMPTS`) | `failed` | `rate_limited` / `RETRIES_EXHAUSTED` | `publish_failed` |
   | 400 migrate / content / 403 / chat not found | `failed` | `rejected` / `CHAT_MIGRATED`, `CONTENT_INVALID`, `DESTINATION_UNAVAILABLE` | `publish_failed` |
   | 401 / 404 from the Bot API (wrong token) | `failed`, and the tick stops dispatching | `rejected` / `BOT_UNAUTHORIZED` | `publish_failed` |
   | timeout, network, 5xx, unparsable, ok without id, transport threw | `unknown`, never retried automatically | `unknown` / `SEND_UNCONFIRMED` (the reason is in the incident `details`) | `publish_unknown` |

3. **Archive** (every tick, even with the kill switch off): see "Post lifecycle as built". One indexed read of the jobs that finished inside the lookback window; only when it finds a qualifying post, one batch of two statements.
4. **Purge** (tick of minute 30, only when nothing was due): one read; only when it finds expired posts, one batch of seven statements (audit row, five child deletes, the posts).
5. **Cleanup**, only on the tick whose scheduled time has UTC minute 0 (read from `controller.scheduledTime`; no state between invocations). Per table at most 100 rows: expired `idempotency_keys`, old `rate_limits` windows, expired `widget_sign_ins`, and ended sessions (revoked, or past both token and hard expiry, 24 h grace) with their `refresh_tokens` deleted first (no `ON DELETE`). Two round trips (platform tables, identity tables). Detached/staged private R2 media is a separate bounded batch (at most 5 objects) on an idle hourly tick; cleanup never delays publication work. Operational retention then runs only when the hourly publication work was idle and no earlier step failed: `job_attempts` older than 90 days are deleted only for terminal jobs with no unresolved incident; resolved incidents older than 365 days and `audit_log` rows older than 365 days are eligible. Each table is capped at 100 rows per tick. Open incidents and attempts belonging to active jobs are preserved. The indexed, replay-safe deletes do not alter job/publication state or send Telegram messages (migration 0030).
6. **Automations**, after publication work and owner alerts only when the tick is idle. Expired five-minute run leases become `unknown`; they are never retried. The two registered Dota automation queues use conditional D1 claims, and pause prevents future claims without cancelling a running operation. Scheduled Telegram publications remain independent. Run history is bounded by migration 0032 and hourly cleanup.

7. **AI video reviews** (stage 5 of `docs/ai/IMPLEMENTATION_PLAN.md`, migration 0072): on idle ticks of minutes 14, 34 and 54 and only while the query budget allows. One `INSERT OR IGNORE` adds a pending row per YouTube/TikTok video aged 74 h–30 days; when reviews are on and the AI budget gate passes, up to two rows limited by `reviews_off`/`budget` go back to pending. At most two reviews per tick: conditional claim with a 5-minute lease and `attempts + 1`, facts and the same-format comparison always, one cheap-model call only when nothing limits it (`settings.videoReviews` is off by default); a provider failure gives the row back, and the third attempt ends as `model_failed`.
8. **Daily analytics report** (AI plan P6, migration 0076): on idle minute-2 ticks (its own slot and statement budget; the minute-8 content alerts send it), only when the owner switched `notifications.dailyReport` on (off by default) and the owner-zone hour has reached `dailyReportHour`. Raised once per owner-zone day as content alert `daily:<date>:v1` (the id is the dedup key, overlapping ticks raise one), sent by the content-alert step with its rules (one attempt, a lost answer stays `unknown`, never resent). Before building it (about 20 D1 statements: forecasts are written and scored with one statement each), forecasts whose horizon passed more than 6 h ago are scored by the reading near the horizon or `no_fact`; the report stores the forecasts it shows (`content_forecasts`). Numbers and text come from code (`modules/content-analytics/daily-report.ts`); no model is called.

Hero statistics (OpenDota, migration 0031) were removed 14.10.2026; their tables stay unused and are no longer polled or purged.

**Automation Center (migration 0032).** One registry row is served: Dota source polling plus watchlist evaluation (the `dota-hero-statistics` row stays in D1 but is not listed since 14.10.2026). `automation_runs` has a unique active-run index per automation and a unique schedule-slot index; HTTP run-now coalesces on that D1 boundary and never calls publication transport. Each idle tick first converts expired automation leases to `unknown` (no automatic retry), then enqueues due slots and claims at most one run for each fixed automation. Pause increments a revision and marks only queued work `skipped`; a run claimed before pause continues. All automation work runs after publication dispatch and owner publication alerts, and is skipped on a busy/failed publication tick. The hourly idle cleanup retains the latest 100 completed runs per automation. Owner-only routes list the fixed registry, history, pause/resume and queue a manual run; no arbitrary jobs, publication controls, cadence mutation or secret data are exposed.

**Manual analytics observations (migration 0033).** Owner-entered `views`, `forwards` and `reactions` are append-only snapshots tied to an already-succeeded publication, with an explicit supported content age, source label, coverage and actor. The server supplies observation time; the insert, audit row and idempotent 201 response commit in one D1 batch. These rows have no FK to deletable publication records and survive their cleanup. They are never collected, inferred, backfilled, edited or deleted automatically. Same-metric/same-age reads use bounded keyset pagination and dedicated indexes; partial coverage requires an explanatory note.

**Message format.** Telegram text is sent as plain `text` plus `entities`, never with a `parse_mode`: trimmed title, blank line, trimmed body — or only the trimmed body for a post created without a title (`posts.title_in_message = 0`, migration 0063, owner 16.10.2026: no title field; its `title` is just the studio name taken from the start of the body, read from `posts` for every revision). Media captions use the same serialization and entities but are capped at 1024; text-only sends are capped at 4096. The title is a `bold` entity at offset 0; approved-body entities are shifted by `title.length + 2` (UTF-16 units). Trimming clips and shifts entities, dropping any left empty. `link_preview_options.is_disabled = true` is explicit for text. Media bytes are read from private R2 as streams and passed to grammY `InputFile`; there is no intermediate whole-file buffer. A mixed 2–10 photo/video group is one `sendMediaGroup` call, with caption/entities on its first item only. Animation in a group, overlong captions, or unsupported combinations fail before the send mark; there is no silent split or truncation. On success, `external_message_ids` stores every result ID and `external_message_id` remains the first for compatibility.

**Idle tick.** With nothing expired, nothing due and nothing finished lately the tick is three indexed `SELECT`s (reconcile, due scan, archive scan; two when publishing is off), no token lookup, no Telegram call, no write, one log line. The archive scan reads the jobs that finished in the last 15 minutes (48 hours on the hourly tick), so its cost follows the recent publishing rate, not the history. Cleanup and purge are not part of it (hourly only). The test pins the query count and a small `rows_read` over 300 finished jobs older than the window.

**Budget per invocation** (Free: 50 D1 queries and 50 subrequests). Per job: 5 round trips (claim, target, revision, send mark, outcome batch), at most 9 statements, 1 subrequest. True worst tick (1 reconciled claim with an incident, a full batch of 2 jobs ending with incidents, one outcome-write retry with its re-read, hourly cleanup and 2 owner alerts): 28 round trips and 49 statements, at most 6 subrequests (2 sends, 2 alerts and up to 2 «Опубликовано» notices, whose origin and settings reads are shared with the alerts), as pinned in `dispatcher-budget.test.ts`; so it fits 50 with no statement to spare even if every statement of a batch were counted as a query (unverified; the repo counts a batch as one). The purge runs on another tick and only when nothing was due: its worst is 6 round trips and 12 statements (reconcile, due, archive scan, expired scan, 7 for the delete, the heartbeat). A test pins these numbers. Calculation, not a load test.

**Wrong token.** A 401/404 fails the job that met it (`BOT_UNAUTHORIZED` + incident) and ends the tick's dispatching, but the next tick will fail the next due job the same way until the token is fixed: switch `PUBLISHING_ENABLED` off first, then fix the secret.

**Settings.** `PUBLISHING_ENABLED` (var in `wrangler.jsonc`, per environment; anything but `"true"` is off; `/api/v1/health` `publishingEnabled` reports the effective state, switch on and token present), secret `TELEGRAM_BOT_TOKEN`. Cron Triggers are declared per environment (`triggers.crons`: `dev` every minute, `production` `[]`), so what runs does not depend on how Wrangler inherits `triggers`; `vars` are not inherited and are repeated per environment.
