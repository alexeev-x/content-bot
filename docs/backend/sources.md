# «Источники»: the night watchman

Status: built. The studio screen is one table of events (status a column; «Показать»: события, пропущенные, прошлые анонсы — the last one temporary) whose row opens a side panel with the whole announcement, its images and links, and the actions. A patch is drafted by a template, a Steam announcement by the AI writer (below).

An event is a non-baseline row of `dota_update_items` (Steam announcements and official patch notes, detected by the Cron watcher). The read model and actions live in `modules/dota` (`source-events.ts` pure rules, `source-events-repository.ts` D1); the draft workflow in `app/workflows/` ties them to `content`. Endpoints: `docs/API_CONTRACTS.md` («Sources events»).

## Classification (best effort)
Fixed at detection, stored in `event_type` (migration 0037 backfills old rows from the title).
- `patch`: every patch-note item.
- `treasure`: a Steam announcement whose title or cleaned opening text matches `treasure`, `collector's cache`, `cosmetic|immortal|arcana|hero|player set(s)`, `сокровищ`, or `набор… косметик|предмет`.
- `news`: anything else. A miss only changes which template the draft uses; the owner edits the draft anyway.

## Status
`hidden` (owner dismissed) wins; else `new` (no draft post yet), `published` (the draft's latest publication job succeeded), `drafted`. `publication.status` is the coarse state of that latest publication (queued, sending, sent, failed, unknown, ...).

## AI draft of a Steam announcement (migration 0090, owner 21.10.2026)
A news or treasure event is written by the AI writer, not by a template. Cron (`processDotaUpdates`) claims `ai_job_id` with a conditional UPDATE (once per event) and sends a `source_event` job to Queue `AI_JOBS`; a refused send gives the claim back for the next tick. The consumer sends «<тип> в Steam: <заголовок> / Пишу пост…» to the owner, fetches the whole announcement from Steam (`GetNewsForApp` up to its date, picked by gid; cleaned, at most 3 500 characters: the feed keeps only 500) and runs the writer in automatic mode with those words as the only facts (then a fact check: one call names the draft's claims its task does not support, and the writer fixes exactly those as a version of the same draft — `modules/ai/fact-check.ts`; series posts too) (`app/workflows/source-event-ai-draft.ts`). The post links to the announcement's dota2.com page (owner, 21.10.2026): Steam's events list, the one dota2.com reads, gives its id by the same post time; when it is not among the 40 latest, the Steam page. The writer appends that link when the model left it out, in every version. The message becomes the usual writer draft (`docs/backend/bot.md` «AI writer»); a failed fetch or model call is said in it, and nothing retries by itself. A failure before that message (D1, Telegram) gives the claim back, so the next tick asks again; no model was called yet. The draft's id is kept in `ai_generation_id`; approving it or one of its rewrites makes the post, which becomes the event's `draft_post_id` (replacing an earlier draft that never went out, e.g. a template from before) with the notice counted as sent (the approval reply has the publish buttons). The sourceAlerts preference does not stop it: the draft is the event's draft, not a notice.

The draft is also shown in the studio's side panel (owner, 21.10.2026) and can be approved there: the same approval as the bot's (`app/workflows/approve-source-ai-draft.ts`), on the exact version shown. While a request is writing (`ai_requested_at`, migration 0091, at most 15 minutes or until the job ends) another one is refused, so one tap is one paid call.

The approved post then gets the announcement's images (owner, 21.10.2026: an event post always carries its picture): the approval queues a `source_media` job; the consumer claims it once, downloads each image from Steam's CDN only (attached as the bot's own file: not listed in «Медиа» and deleted with its post, a sent one included — owner, 22.10.2026, migration 0099) (its mirrors in turn when one refuses; an image Valve's CDN refuses to the Worker — every host answered 403 to Cloudflare for the event page's images on DEV — is fetched by Telegram: the bot sends it to the owner's chat silently by its address, takes Telegram's JPEG and deletes the message; a redirect only within steamstatic.com; a skipped image is logged with its code) (at most 10, each within the photo limit) and attaches it through the upload use case (same checks, an idempotency key per image, a stale revision retried), and tells the owner only when some did not arrive (owner, 22.10.2026: no message when all are attached). A failure leaves the text post as it is and says so. «Прикрепить картинки из анонса» in the side panel (`POST …/images`) runs it again for the event's post. Every address in an approved AI text hides behind its words (owner, 21.10.2026: «все ссылки вшивай в текст», `linkTrailingSource`): «Посмотреть наборы: https://…» becomes «Посмотреть наборы» as a link; an address alone on its line links the line above when that line ends with a colon, else becomes «Подробнее»; one inside a sentence becomes «ссылка».

«Написать через ИИ» in the side panel (`POST …/ai-draft`) asks for any announcement, a past one included: the claim is taken again, the row stops being baseline (it is an event from then on), and the same job runs. The earlier draft stays linked until the new one is written; a draft from a replaced job that finishes later is not. A replay the queue refused keeps its claim (released, the row would look new to Cron); the owner taps again. The «draft» endpoint still makes a template draft of any event; the studio calls it only for patches.

### Rich format of every source post (owner, 23.10.2026)
Every task of a source's writer opens with «Повод:» and, but for the patch (below), asks for the structure
`SOURCE_POST_STRUCTURE` (`app/bot/rich-post.ts`): a short heading line, paragraphs, «• » lists, «Название — что
важно» rows (a table, with an optional «Колонка | Колонка» head), «▾ Заголовок» folding the rest, the link last. The
draft stays that plain text in the bot; an approval of a draft whose first generation's task opens with «Повод:» turns
it into rich HTML (`structuredRichHtml`; the owner's own drafts stay classic), the post's media going into the
`{{media}}` slot after the heading (one picture or a slider). A text without a heading line stays a classic post.

## Patch posts (owner, 22.10.2026)
A Steam announcement whose title names a patch version («7.41f Gameplay Patch», «Update 7.37 Is Here», «… in the 7.38 Gameplay Update», «Introducing Largo and Patch 7.40»; `patchVersionOf` in `modules/dota/patch-digest.ts`) is written as one post from Valve's notes of that version, not from the announcement's few lines, and never as an event-page series, its own page or not. The consumer reads `datafeed/patchnotes` and the hero and item names (`digestOfficialPatch`): Valve's general notes first (facets removed, a mechanic, the map, modes), then the heroes and items by how many notes they have, each with all its notes as Valve wrote them (`patchNotesText`). The writer gets them whole beside its task (owner, 23.10.2026: «он должен получать максимальные данные»; a 3 400-character digest left 7.41f's post with no buffed hero): the task holds the instructions within its 4 000 characters, the notes go to `ai_generations.facts` (migration 0105, at most 60 000), which every rewrite, fix and fact check of the draft reads too. Notes up to 40 000 characters go whole (7.41f: 5 500); a bigger patch (7.41: 120 000) is first read by the cheap model (`modules/ai/patch-condense.ts`: every hero and item with its direction and numbers, the wording and repeats dropped), and cut to 40 000 when that fails. An announcement's whole text goes the same way. The task (`patchTask` in `app/workflows/source-event-ai-draft.ts`) asks for one post in order: the main change first (a short joke welcome), who was cut and who was buffed the most (2–4 heroes each), the items that changed most; the rest is left to the linked `dota2.com/patches/<version>`. The post opens with «Вышел <version>.» on its own line: the task asks for it, and `aiPostText` (`app/bot/draft-from-message.ts`, every approval: the bot, the studio, the automatic publishing) makes that line bold and puts an empty line after it (owner, 23.10.2026); no other post gets a bold first line. While Valve has no notes for the version, the post is written from the announcement as any news. A «Dota 2 Update - <date>» hotfix that Cron asked for first goes through one cheap call (`modules/ai/hotfix-check.ts`, the cheap model, JSON `{worth, reason}`): nothing for a player in it, and the event is finished without a draft or a message to the owner; a check that cannot answer lets the writer go on. The owner's own «Написать через ИИ» is always written. The datafeed's own patch event keeps its template draft (below) for the studio.


Since 23.10.2026 (owner: every post in the approved rich format) the task asks for a fixed structure: «Вышел <version>.»,
the main change, then «🔴 Порезали сильнее всех», «🟢 Усилили», «🟡 Почти не изменили» with «Герой — что поменяли» lines (usually
two, three or four only when something really interesting happened to them, never more than four; the cut and buffed
all three groups always, at least two heroes each, owner 23.10.2026; the writer never says what it was or was not given) (heroes named as players call them, «Котл»), then «Предметы» with 2–4 lines. The draft stays this plain text in the
bot; every approval (bot, studio, automatic) turns it into rich HTML (`app/bot/rich-post.ts` `patchRichHtml`): a heading,
the media slot `{{media}}` for the patch picture (filled at sending, contracts `expandRichMedia`), the main change, one
table with the groups as header rows, the items in a folded block and «Подробнее» to the patch page. A text without the
structure keeps the classic post.

### Patch picture (owner, 22.10.2026)
A patch announcement's post gets one drawn picture instead of the announcement's images (`app/workflows/patch-picture.ts`, passed to `attachSourceEventImages` as `patchPicture`, both on the automatic publishing and on the owner's approval). A versioned patch shows its version and the heaviest 1–4 of «Баланс героев», «Изменения предметов», «Обновления карты», «Правки механик», «Режимы игры» (`patchPicturePoints`: changed heroes, changed items, notes of the map, other and mode sections of Valve's general notes); with fewer than three of them «Таланты героев» and «Нейтральные предметы» fill in (owner, 23.10.2026: at least three; 7.41f has heroes and items only); a hotfix («Dota 2 Update») gets its own cover (owner, 24.10.2026: unlike a patch's): `drawHotfixPicture` sends the owner's three references (`design-refs/hotfix-cover/` 1–3, built into `hotfix-cover-refs.generated.ts`); the cheap model reads the hotfix and the 8 newest announcements' titles and returns a scene of what is current in the game (an event, its place; never a character) and a 1–3-word Russian caption of the main change («Баланс героев», «Исправления ошибок»); the cover is that scene darkened, the Dota logo, «ОБНОВЛЕНИЕ» and the caption, read back like a patch's; an unusable answer keeps a dark Dota valley and «Исправления ошибок»; a patch without Valve's notes keeps the announcement's images. `drawPatchPicture` (`modules/ai/patch-picture.ts`) sends the owner's four references (`design-refs/patch-cover/` 1–4 at 768×384, built into `patch-cover-refs.generated.ts`) to OpenAI's image edits (`gpt-image-2.5-sunburst`, 1536×768 JPEG — 2:1 like the owner's 1000×500, which the model cannot draw: sides must be multiples of 16 and at least 655 360 pixels — quality medium, 150 s) in a colour the cheap model picks for the patch's content from six, never the last cover's (owner, 23.10.2026; `system_state` `patch_cover_theme`; a failed pick is random among the rest), the same on every try, then `gpt-6.1-sol` reads the number and captions back (an `input_image` part; case, «ё» and line breaks aside). A difference or a provider failure is another try, at most three and none started after 4.5 minutes; then the post goes without a picture (also when the upload refuses it) and the owner's bot message says so. Valve's feed failing keeps the announcement's images. It needs AI on, the OpenAI key and budget left for the read-back model; each call writes one ledger row (`other` for the picture, priced from OpenAI's page of 23.10.2026: $8 per 1M input tokens, all counted as image input, and $30 per 1M output; `check` for the read-back), and «ИИ» → «Деньги» shows the pictures as their own line «Картинки к патчам» and nothing else, so three tries stay inside the Free plan's 50 subrequests. The automatic publishing approves a patch post and hands it to a queue job of its own, `patch_publish` (QA 23.10.2026: the writer and three tries do not fit one invocation): it draws and attaches the picture, publishes with the event's key `autopublish:<externalId>` (a redelivered job claims once and never doubles it), and sends the owner one quiet note; the writer's note says the post is approved and the picture is being drawn. With the automatic publishing switched off meanwhile, the approved post waits in the studio. Queuing a picture job (`source_media`, `patch_publish`, their continuations; `app/workflows/picture-jobs.ts`) marks the post `media_pending_until` = now + 15 minutes, and its last message clears it (the automatic publishing clears it just before its own approval and publication): until then the studio shows «Создаётся изображение» and nothing is approved or published (owner, 23.10.2026). Base64 is decoded natively (`node:buffer`): a JS loop over a picture costs the Free plan's whole 10 ms of CPU.

## Auto-draft at detection (patches)
`processDotaUpdates` (Cron, every 5 minutes, idle ticks only) makes one template draft per new patch: it reserves `draft_post_id` with a conditional UPDATE, then `createPost` with the idempotency key `dota:<sourceKey>:<externalId>`. The owner's «draft» endpoint uses the same reservation and key, so Cron, the endpoint, a re-detection and a rerun leave one post. Hidden events are skipped.

Templates (Russian, in `source-events.ts`; they only rearrange source text, never generate facts, never copy images):
- patch: title `Патч <версия>: что изменилось`; body lists changed heroes and items from the stored parse, watched ones first, at most 15, then `и ещё N`; if the notes are not parsed it says so; then `Источник: <url>`.
- treasure (screen «draft» only): title `Новая сокровищница: <название>`; first sentence of the announcement; link.
- news (screen «draft» only): the title; first sentence of the announcement; link.
The announcement text is Steam's first 500 characters, cleaned of BBCode/HTML, links and image macros, kept in `excerpt` (at most 600).

## Owner notice
After the draft exists the workflow claims `owner_alert_claimed_at` (one conditional UPDATE: once per event) and sends `<тип>: <заголовок> — черновик готов` with the publish keyboard from `app/bot/publish-keyboard.ts` («Опубликовать сейчас → канал», «Открыть в Студии»); the buttons come from `createPublishActions`. The `sourceAlerts` preference off means the claim is consumed and nothing is sent. A failed send is logged, not retried (the claim is spent).

## Budget (Free plan: 50 subrequests per invocation)
The workflow takes `container.queryBudget`: it charges the feed and detail fetches and the Telegram send, and skips drafting (13 left needed) and notices (9 left) when what remains would not leave room for the rest of the tick (12). Leftovers are picked up by the next 5-minute slot. Pinned by `tests/integration/source-events.test.ts` (tick within 50) and `dispatcher-budget.test.ts`.

## Series of an event with its own page (migration 0092, owner 21.10.2026)
When the announcement links an event page on dota2.com (`/darkcarnival`), the `source_event` job plans a series instead of one post (`app/workflows/source-event-series.ts`). The page is a React app: `modules/dota/event-page.ts` follows its HTML to the main bundle and the chunk manifest, finds the page's code chunk and its localization chunk (Russian when Valve translated it, else English) by stable shapes, decodes the texts without evaluating anything and collects the page's media (Valve's CDN, decoration and webm left out); five requests, about 1 ms to scan the bundle. Every event gets a page of its own (owner, 22.10.2026: the content must be taken whatever the page), so only shapes shared by the pages of 2023–2026 are matched: the app's own route name when it is not the address (`patch738` is `/wanderingwaters`), texts emitted as `JSON.parse('…')` or ``JSON.parse(`…`)``, up to 400 texts and 60 000 characters. The treasure is read from its slider (slides written out, a map over `[{heroname:…}]`, or a map over a count): each set's hero, name and image (`…/<folder>/<video>.png` on Valve's video CDN), in slider order, which is rarity from common to rarest; without a slider the sets come from the texts' hero/set pairs and the order counts as unknown. What could not be read (texts cut off, no media, no treasure order, sets without images) is logged and sent to the owner («Страница … прочитана не полностью: …»); the series is still planned. The page's priced items (an automaton persona: `nItemID` next to its name key) get Valve's price (`modules/dota/valve-store.ts`, `dota2.com/react/getbpprices`, keyless, dollars) as one more text, «Цены в магазине Dota 2 (Valve): Axe — $14.99; …» (owner, 22.10.2026). The planner gets the treasure as one text by rarity (the last set named the top reward) and each set's image named by hero and set. One model call (`modules/ai/series-planner.ts`) plans 1–3 posts on fixed topics in this order, a topic the page lacks skipped (owner, 22.10.2026: five were too many): the event itself (what players do and its rewards; always there), the new hero cosmetics (personas, one image each), the new treasure (its post opens with the rarest set's image whatever the plan chose); no repeats, the text keys and media each one takes; unknown keys and media are dropped, a plan without facts falls back to the one post. The plan is stored (`source_series`, `source_series_posts`) and one `series_post` job per post writes it with the writer in automatic mode from its own facts (the link line is the page). The last finished post claims the owner's one notice («Серия постов … готова»). Once stored, a series never falls back to the one post: a post whose job the queue refused is marked failed, and one still writing after 20 minutes reads as failed. A single draft written later replaces the series in the studio (the newest request wins). Series posts are written to be lively, not a dry summary (pack rule «Серия постов о большом событии», owner 21.10.2026). The studio's side panel shows the series; each post is approved on its own, or all ready ones at once («Одобрить все»), into its own studio post (`POST …/series/{postId}/approve`); one post can be rewritten by a ready instruction or the owner's own words (`…/rewrite`, the writer's rewrite of exactly the version shown), which then gets the images its plan chose: photos only, never videos (owner, 22.10.2026, after two event videos made a 97 MB album Telegram could not take in time); a post that shows several heroes, personas or sets gets one image each, up to 10 (a Telegram album). A picture with its background is preferred (owner, 22.10.2026: a cut-out PNG shows on white): the planner is told so, and a planned PNG gives way to the one JPG of its own folder (an automaton's gameplay frame); with no JPG there, or several, it stays. A page that cannot be read leaves the event to the one post from its announcement.

## Automatic publishing (owner, 21–22.10.2026)
Settings → Общие → «Автопубликация» (`OwnerOperationsSettings.autopublish`: off by default, a channel, a daily limit the owner types, 1–100, default 3; each change is confirmed in a small dialog, the limit saved by its own «Сохранить», owner 23.10.2026). Only Cron's first draft of a new event (`source_event.automatic`; the owner's «Написать через ИИ» replay never) whose fact check found nothing unsupported (`WriterResult.factCheck = clean`: the first draft, or its fix checked once more and found clean, owner 23.10.2026; a fix still flagged, or an unchecked draft, never) is published without the owner (`app/workflows/autopublish-source-event.ts`). Checked first, before anything is written: the switch and an enabled channel, and the limit (`publication.create` audit rows of the actor `autopublish` in the last 24 h; two events at once may pass it by one). Any refusal there leaves the owner the draft as before, with a line saying why («⏸ Не опубликовано без вас: …», also for a fact check that was not clean; owner 23.10.2026). Then the AI draft becomes a studio post as `OWNER_PREAPPROVED` (actor `autopublish`, no `source_media` job), up to 4 of the announcement's pictures are attached at once (one queue message stays inside the Free plan's subrequests), the post is approved and a «now» publication is created to the channel with the key `autopublish:<announcement id>`. From the approval on, the draft can no longer be edited, so a later failure (no picture arrived, the channel refused) leaves the post in the studio and the bot says so: «Не опубликовано без вас (…): «…». Пост ждёт в студии». With it on, Cron's «Пишу пост…» is sent without sound; a published one becomes «Опубликовано без вас: «…». Открыть» (an edit, silent too), and a draft that goes to the owner arrives silently as well. Switching it off is the stop button.

**A series (migration 0100, owner 22.10.2026).** A series planned from Cron's draft is `source_series.automatic`, and each post keeps its fact check (`source_series_posts.fact_check`). When the last post is written and every post is ready and clean, no «Серия готова» note is sent: `series_publish` jobs run one post per queue message, then one more for the publication (`app/workflows/autopublish-series.ts`; each message stays inside the Free plan's queries and subrequests). The first step checks the switch, an enabled channel, the limit (a series counts once) and that nobody touched the series: every post is still its first, fact-checked version with no rewrite or owner edit, and none is in the studio yet (QA 22.10.2026). Refused there, the owner gets the usual note. Each post step checks its post again, approves it into a studio post (`OWNER_PREAPPROVED`, actor `autopublish`), attaches up to 5 of its pictures and approves the post. The publication step refuses if the switch went off or any of the posts already has a publication (one the owner made by hand meanwhile), else creates the series publication (`autopublish-series:<series id>`, now, 10 minutes apart). Notes are silent while the automatic publishing is on; a step that stops says the posts wait in the studio, where «Опубликовать серию» publishes them; a step whose Worker dies is reported by Cron's lost-job check (its claim carries the chat). With the switch off, a Cron series' «Серия готова» keeps its sound.


A test on DEV (owner, 23.10.2026): the side panel's «Проверить автопубликацию (DEV)» (shown on the dev build for a Steam announcement without a post) asks for the AI draft with `autopublishTest`, so the job is `automatic` as Cron's own and takes the same way: the hotfix check, the writer, the fact check, the approval and publishing when the automatic publishing is on (a patch through `patch_publish`). ## Picture quality (owner, 23.10.2026: a project law, `docs/DECISIONS.md`)
Every picture a source post takes (`attachSourceEventImages`) is checked before it is attached: its size is read from
the PNG, JPEG or WebP header (`app/workflows/picture-quality.ts`); narrower than 800 px, it goes through OpenAI's image
model with the instruction to change, add and draw nothing, only to make it sharper (`modules/ai/picture-enhance.ts`,
paid per picture). A GIF, an unknown format, a failure or a job past its 8-minute budget keeps the original picture.

Pictures are attached one per queue message (QA 23.10.2026, measured: one costs about 13 D1 statements, its
improvement about 5, the last message's approval and publication about 20, the Free plan allows 50; the daily limit is
counted again before that publication): an automatically approved post (`patch_publish`, now every source
post, not only patches), a series step (`series_publish`) and the owner's approval (`source_media`) each send their
own next message with `from` until no picture is left; only then is the post approved and published. Liquipedia's
icons are fetched 2 s apart.

## Treasure follow-ups from Liquipedia (migration 0101, owner 22.10.2026)
A treasure announced without its own event page (Cron's `treasure` event, not baseline, not hidden) is followed for 6 hours after Valve's announcement. Cron's Dota step queues one `treasure_watch` job per run (every 5 minutes on idle ticks; no D1 query of the tick: the consumer reads the app origin itself); the consumer (`app/workflows/treasure-watch.ts`) starts a watch for each such treasure (`treasure_watches`) and serves at most two per run. A run takes each watch by a conditional update of its `checked_at`, the first only when no watch was taken in the last 3 minutes, so two runs never talk to Liquipedia at once and never queue the same follow-up; the watch is saved as of that claim before its follow-up is queued. Liquipedia's MediaWiki API only (`modules/dota/liquipedia.ts`; its terms forbid anything else; since 23.10.2026 the set icons the API's `imageinfo` names are fetched from its commons too, 2 s apart, the owner to confirm this fits the terms): 2 s between requests (also between watches), a User-Agent naming the project, its repository and a contact e-mail. The page is found by asking which phrases of two words or more of the announcement's title exist as pages («Inside the Trove of Terror» → «Trove of Terror»): of the three longest, the first whose infobox says it is a treasure. Each run asks for the page's latest revision; on a change the wikitext gives the sets by rarity, the opening bonuses, a short summary of the drop rates (only once its table has rates; sets only from level-3 sections, so «See also» is not a rarity) and the treasure's item id, whose price comes from Valve (dollars). Facts are compared one by one (each set by name, each bonus by its condition, the drop rates and the price once): a fact once told never goes again, even with another text, and what waits is rebuilt from the page as it is now, so a name corrected meanwhile goes out corrected. What is new waits until the page has been quiet for 30 minutes and then becomes one `treasure_post` (the sets alone are enough, the rest go at least two together; at the window's end anything left goes once); at most two follow-ups per event, and none before the event's own post went out to a channel (the follow-up says the treasure was told). The follow-up is written like Cron's event draft (automatic mode, fact check, the Liquipedia page linked, «по данным Liquipedia», the price «по данным Valve») and, when the automatic publishing allows, published without the owner under its own key (`autopublish:<id>:follow-up-<n>`), with its sets' icons when it tells sets (owner, 23.10.2026) and not as the event's own post; otherwise the owner gets the draft. A treasure whose event got its own page's series is told there, and a hidden event is not told: either watch ends.

## Changes in the game's files (migration 0107, owner 23–24.10.2026)

Required before the release and published like every source post (owner, 24.10.2026). Source: the GitHub repository
SteamTracking/GameTracking-Dota2 (SteamDB's tracker, one commit per game build), read with the owner's no-scope token
`GITHUB_TOKEN` (`integrations/github/github-api.ts`); without the token the source is off. Never steamdb.info itself
(its FAQ forbids scraping); the post names no SteamDB or GitHub and links nothing.

- Every Dota run of the Cron queues `game_files_watch` next to the treasure watch (`app/workflows/game-files.ts`). A run
  reads the 10 newest commits. The first run only records them as the baseline (`game_file_builds`, `skipped`).
- A new commit's message («6964 | 11 files | M\t<path>, …») decides whether it is read: relevant are
  `pak01_dir/scripts/npc/**`, `pak01_dir/resource/localization/*english.txt`, `pak01_dir/scripts/*.vdata` and
  `pak01_dir/patchnotes/**` (`modules/game-files/build-diff.ts`). The tracker cuts the message at about 1 000
  characters, so a build whose message names fewer files than its count is always read (QA 24.10.2026). A build
  naming every file and none of these is recorded as skipped unread.
- One build is read per run, oldest first, as its plain unified diff (not JSON: a big build's JSON costs most of the
  Free plan's 10 ms of CPU and lists only 300 files); only the file headers are scanned to pass the rest. A diff over
  3 MB, or one GitHub refuses to make, is `skipped` (`too_big`): a big patch's build is about 30 MB, and its changes come
  through Valve's patch notes source. A network failure, a rate limit or a revoked token leaves the build for the next
  run; the queue log names the code (`GITHUB_RATE`, `GITHUB_TOKEN`).
- A build's diff keeps only the changed lines of those files, «- old» / «+ new», without moves, spacing-only changes,
  braces and block keys, at most 3 000 characters a file and 14 000 a build (cut at 15 500, under the job's 16 000).
  Nothing left: `skipped` (`no_changes`).
- The build is claimed once (`queued`, `INSERT OR IGNORE`) and becomes a `game_files_post` job, which claims itself
  again under a second id before anything paid, so a redelivered copy does nothing. A cheap call (`gameFilesWorthPost`)
  says whether a player would care; a dull build becomes `skipped` (`not_worth`) and the owner hears nothing. A check
  that cannot answer lets the writer go on.
- The writer's task (`gameFilesTask`): the text opens with «В файлах игры нашли», says Valve has not confirmed it and it
  may change, retells the changes in Russian, no heading and no link. Then, owner 24.10.2026: changed numbers or dates
  as lines «Название: было → стало» (values joined by «/»), which `findRichHtml` (`apps/contracts/src/post-rich-text.ts`)
  turns into a rich post: the text and one table «Было / Стало», each value's name on a row of its own so a phone does
  not wrap; with no numbers, a «```diff» block of the real changed lines, verbatim, which `aiPostText` turns into a
  `pre` entity in the `diff` language (red and green in Telegram) of a classic post — a rich message draws code badly
  on phones. The build's changes are the source's facts, checked by the fact check like any automatic draft. Anything
  a player could notice is worth a post, cosmetics included («давай всё публикуем»); a build that adds Valve's patch
  notes (`"DOTA_Patch_…"`) is `skipped` (`official_patch`): the patch notes source tells it.
- Publishing: the event writer's job with its own task (`own`), the key `autopublish:files:<sha>` (one publication per
  build), `standalone`: no event link and no announcement pictures, through `patch_publish` like every source post. A
  text with an address in it waits for the owner (`link`): GitHub's text is nobody's, and an address would go out as a
  hidden link. Off, over the daily limit or with an unclean fact check, the draft comes to the owner as any source draft.
- Known gap: a run stopped by the platform between the claim and the queue send leaves the build `queued` with no post.
- A build with nothing worth a post (owner, 24.10.2026: «если ничего не нашлось можно смешную добавить текст и сам
  diff»): the newest build of a run that touches nothing a player sees, one whose diff has no changes, and one the cheap
  check finds dull get one short post — a joke the cheap model writes on a theme drawn at random («шуточные посты
  всегда разные», `modules/ai/quiet-build-joke.ts`; a stand-in line when it cannot, or when its joke lacks the build
  number), asked only once the post may go out — and the version lines as a
  ```diff block (`- ClientVersion=<previous>` / `+ ClientVersion=<build>`), key `files-quiet:<build>`, under the
  automatic publishing's switch and limit (`app/workflows/publish-fixed-post.ts`). A build one of whose commits had a
  find gets none; an official patch build none either (the patch notes tell it). The post is its own queue job
  (`game_files_quiet`, its own D1 budget), sent ten minutes late so the other commits of the build are read first; it
  claims the build once before the joke is paid for, checks again that no commit of the build had a find, and a run
  queues at most one (QA 24.10.2026).

## Early signal of a Dota build from Steam (migrations 0108, 0113; owner 24.10.2026)

Steam's own product info (PICS), read the way a Steam client reads it: every Dota run of the Cron queues `steam_watch`
next to the game-files watch (`app/workflows/steam-watch.ts`). The run asks `ISteamDirectory/GetCMListForConnect` for
the WebSocket connection managers, keeps those on port 443 (a Worker reaches only some ports), opens one with the
Worker's WebSocket upgrade, logs on anonymously and sends one product info request for Dota 2 (570), then closes
(`integrations/steam-cm/steam-cm-client.ts`: the few protobuf fields by hand, a gzipped Multi unpacked with
`DecompressionStream`; no Steam library runs in a Worker). DEV reads it in about 2.4 s.

A new public build is no news by itself (owner, 24.10.2026: «мне нет смысла от сборки»: build 6967 changed two binaries
and nothing a player sees, and such builds come twice a week). Nothing is posted and the owner is not told. The build
starts the digging: `steam_app_watch.files_due_until` is set an hour ahead, and every idle Cron minute until then queues
the game-files watch (one indexed read a tick), so a find goes out as soon as GameTracking-Dota2 has the build (about a
quarter of an hour after Steam ships it). The first read is the baseline; a higher change number moves the row with a
conditional update, so overlapping runs act once; a read without the build never counts as a new one.

Both watches (game files and Steam) write their last run to `source_watch_checks` (migration 0109): a successful read
or the failure's stable code. «Источники → Состояние лент» shows them beside the two feeds (`GET /api/v1/dota`
`watches`).
A watch whose third run in a row fails raises one content alert «Источник … не работает» with its code (`watch-down:<key>:<time>`, review 24.10.2026), sent with the next content alerts.
