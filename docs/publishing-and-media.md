# Публикации и видео

Детали к разделу «Публикации и видео» из `../README.md`. Архитектурные правила — там, здесь механика.

Одна запись публикации = одна площадка + один аккаунт. Она закрепляет конкретную версию материала,
описание, файл и время. Правка черновика её не меняет без отдельной команды. Одобрение материала и
статус публикации — разные состояния: YouTube может быть опубликован, пока TikTok в ошибке.
Успех на одной площадке не повторяется из-за ошибки другой.

### Как ролик попадает в R2

Типичный размер — **200–250 МБ**. Лимиты Telegram здесь асимметричны, и путать их дорого:

| Операция                                 | Кто выполняет             | Лимит                                       |
| ---------------------------------------- | ------------------------- | ------------------------------------------- |
| Автор отправляет видео боту в чат        | клиент Telegram (MTProto) | **2 ГБ** (4 ГБ с Premium)                   |
| Бот получает сообщение                   | Bot API                   | приходят метаданные и `file_id`, байтов нет |
| Бот **скачивает** байты (`getFile`)      | Bot API                   | **20 МБ** — жёстко                          |
| Бот **загружает новый** файл (multipart) | Bot API                   | 50 МБ (фото 10 МБ)                          |
| Бот **пересылает по `file_id`**          | Bot API                   | **без ограничений**                         |

То есть залить ролик в бота можно хоть на гигабайт — это делает клиент Telegram, а не бот.
Нельзя другое: **вытащить эти байты обратно**. Бот знает `file_id`, файл лежит на серверах Telegram,
но `getFile` откажет всему, что больше 20 МБ.

Отсюда два следствия:

- **Публикация в Telegram-канал работает при любом размере** — бот пересылает ролик по `file_id`,
  ничего не скачивая. Для этого сценария отправка файла боту в чат и есть правильный путь.
- **YouTube и TikTok требуют сами байты**, поэтому для них файл должен попасть в R2 мимо Telegram.

### Почему 20 МБ существуют и как их снимают

Лимит принадлежит **HTTP-слою Bot API**, а не Telegram: `api.telegram.org` обязан сначала скачать файл
себе на диск, поэтому и ограничивает размер. У самого протокола **MTProto такого лимита нет**. Отсюда
два обхода, и оба требуют постоянно работающего процесса вне Workers:

1. **MTProto-клиент** (Telethon / Pyrogram / GramJS). ⚠️ **Юзербот не нужен**: MTProto авторизует и
   ботов (`api_id` + `api_hash` + `bot_token`), и бот-сессия читает файлы без ограничения в 20 МБ.
   Личный аккаунт автора в систему завязывать не требуется — это безопаснее userbot-сессии.
2. **Локальный Bot API server** (`telegram-bot-api`) — тот же результат ценой демона на C++ с диском.
   MTProto-клиент легче.

❌ Внутри Worker это не живёт. TCP у Workers есть (`connect()` из `cloudflare:sockets`), но MTProto
шифрует весь поток: чтобы скачать 250 МБ, их надо расшифровать в JS — чистый CPU против лимита 10 мс
на Free. Нужна постоянная машина: бесплатная always-free VM или VPS.

### Ingest как сменяемый драйвер

Модуль `media` объявляет контракт «получить байты материала в R2» и знает только о нём. Драйвера два,
выбор между ними не трогает остальные модули:

- **`upload` — реализуем.** Mini App + R2 multipart, описан ниже. Ноль инфраструктуры, ноль денег.
- **`mtproto-agent` — не реализуем, шов сохраняем.** Маленький постоянный процесс вне Cloudflare:
  получает задание (`file_id` → ключ R2), качает бот-сессией по MTProto, стримит в R2 по
  S3-совместимому API, отчитывается о прогрессе. Воркер остаётся мозгом, агент — тупой трубой.

**Решено 19.09.2026:** строим `upload`. Бесплатность и один рантайм важнее привычного «отправил боту в
чат»; при трёх роликах в неделю второй хост не окупается. К `mtproto-agent` возвращаемся, только если
загрузка из Mini App окажется неудобной на практике — например, автор заливает в основном с телефона
и ловит обрывы.

Основной путь — **прямая загрузка в R2 мимо Telegram**:

1. Бот отдаёт одноразовую ссылку с коротким TTL на страницу загрузки. Токен одноразовый, привязан к
   материалу и владельцу. Сделать её **Mini App** стоит сразу: страница открывается внутри Telegram,
   автор выбирает файл и видит прогресс, не выходя из чата — по ощущению это та же «отправка боту».
2. Страница режет файл и грузит **частями по 20–50 МБ**: тело запроса к воркеру на Free ограничено
   **100 МБ**, части заведомо в него укладываются. 250 МБ → около 10 частей.
3. Воркер ведёт R2 multipart (`createMultipartUpload` → `uploadPart` → `complete`), тело части отдаёт
   в R2 потоком (`request.body`), в память не читает. Части R2: минимум 5 МБ, кроме последней.
4. Загруженные части и `uploadId` пишем в D1 → прерванная загрузка продолжается, а не начинается заново.
5. S3-подпись и `aws4fetch` не нужны: всё идёт через биндинг `BUCKET`.

Запасной путь без UI: автор присылает **прямую https-ссылку**, воркер тянет файл `Range`-запросами
кусками в ту же multipart-загрузку, по куску за вызов задания. Тот же прогресс в D1.

### Как ролик уходит на площадки

- **YouTube** — только push байтов, pull-from-URL нет. Используем **resumable upload**: сессия
  создаётся один раз, дальше `Content-Range`-чанками, при обрыве сервер сам сообщает подтверждённый
  offset. Читаем из R2 `Range`-ом и шлём **по одному чанку за вызов задания**, offset — в D1.
  Так укладываемся в 10 мс CPU (это I/O, не счёт) и переживаем любой рестарт.
  Квота, проверено 19.09.2026: **100 вызовов `videos.insert` в сутки**, по 1 unit отдельного
  bucket Video Uploads ([документация](https://developers.google.com/youtube/v3/docs/videos/insert)).
  Для непроверенных API-проектов, созданных после 28.07.2020, загрузки приватны до аудита.
- **TikTok** — есть **`PULL_FROM_URL`: площадка скачивает файл сама** по нашей https-ссылке.
  Это предпочтительный путь — байты через воркер не идут вообще. Требуется верификация домена или
  URL-префикса в портале TikTok и ссылка **без редиректов**, то есть нужен свой домен на воркере
  (`r2.dev` не подойдёт — он не наш). Если верификация недоступна, остаётся `FILE_UPLOAD`
  последовательными чанками 5–64 МБ (последний до 128 МБ), максимум 4 ГБ — та же схема, что с YouTube.
- ❌ Целый ролик в память Worker не читаем ни на одном шаге.

### Хранение и очистка

Файл можно удалять через **N дней после последней успешной публикации** на всех выбранных площадках
(отсчёт от публикации, не от загрузки). `N` — настройка, по умолчанию 7. Ежедневная очистка перед удалением перепроверяет, что файл не
нужен ожидающей, выполняющейся или требующей повтора публикацией — в том числе в другом материале.
Ошибка очистки логируется и повторяется; удаление отсутствующего файла — успех. Тексты, история и
ссылки на опубликованное остаются в D1. Отменённые и неопубликованные файлы показываем владельцу
отдельным решением, чтобы не копились.

**Реальный объём канала: в среднем 3 ролика в неделю, пик — один в день и редко.** При 250 МБ на ролик
это 750 МБ в неделю, то есть при семидневном хранении в R2 одновременно лежит **около 1 ГБ — порядка
10% бесплатных 10 ГБ-месяц**. Даже месяц по ролику в день даёт ~1,75 ГБ одновременно. Операций тоже
почти нет: ~12 Class A на загрузку (multipart) плюс чтения на отдачу — сотни в месяц против
1 млн / 10 млн бесплатных.

Следствия:

- Хранилище на этом объёме **не является ограничением**, и оптимизировать его заранее не нужно.
- Срок хранения — **настройка, а не вынужденная экономия**. 7 дней после последней публикации —
  значение по умолчанию; 30 дней при таком потоке дают ~3,2 ГБ, то есть втрое ниже бесплатного лимита,
  и полностью снимают риск «удалили раньше, чем понадобилось». Значение меняет владелец.
- Незавершённые multipart-загрузки место всё равно занимают — прибираем тем же cron'ом.
- Узкое место первого этапа — **качество и квота ИИ**, а не R2 и не квота YouTube
  (план — 3 ролика в неделю; фактические квоты проекта проверяем перед подключением).
