# Установка и подключение

Разработка идёт **на двух машинах: macOS (zsh) и Windows (PowerShell)**. Node 24, pnpm 10, wrangler 4.
Команды `pnpm` одинаковы в обеих системах; различия — только в мелочах, они отмечены ниже.

## Одинаковость двух машин

Чтобы репозиторий не «дёргался» при переходе между ОС:

- **`packageManager: "pnpm@10.x"`** в `package.json` + Corepack — обе машины берут одну версию pnpm,
  глобальная установка значения не имеет.
- **`.gitattributes` с `* text=auto eol=lf`** и `"endOfLine": "lf"` в `.prettierrc` — иначе Windows
  запишет CRLF, и весь файл покажется изменённым. `core.autocrlf` при этом оставляем `false`.
- **Скрипты `package.json` — только кроссплатформенные**: бинарники из `node_modules` и `node`.
  ❌ `rm`, `cp`, `mkdir -p`, `export VAR=`, `$(...)`, `.sh`-файлы. Нужен шаг сложнее одной команды —
  пишем `scripts/<имя>.js` на Node (он одинаково работает везде), а не цепочку через `&&`:
  в PowerShell 5.1 `&&` не поддерживается.
- **Husky на Windows** работает через Git Bash (ставится вместе с Git for Windows). Хуки пишем на
  POSIX sh, без bash-измов.
- В импортах **регистр букв соблюдаем точно**: macOS и Windows его прощают, рантайм Workers — нет.

> Локальная разработка работает полностью. Не выполнялся только деплой: в `wrangler.jsonc`
> заглушки вместо `database_id`, для их получения нужен `wrangler login`.

## Команды

```bash
pnpm dev          # разработка: миграции, воркер и мост Telegram -> воркер
pnpm check        # типы, линт со слоями, формат (он же на pre-push)
pnpm fix          # то же, но с автоисправлением
pnpm deploy:dev   # миграции D1 + деплой воркера в dev
pnpm deploy:prod  # то же в production
pnpm cf-typegen   # типы биндингов, после ЛЮБОЙ правки wrangler.jsonc
pnpm bot          # проверить бота и выставить меню команд
pnpm test         # тесты внутри workerd
pnpm skills       # разложить скилы из docs/skills по папкам агентов
```

Флаги, которые нужны редко:

| Команда                          | Зачем                                              |
| -------------------------------- | -------------------------------------------------- |
| `pnpm dev --no-bot`              | только воркер, апдейты слать curl'ом               |
| `pnpm dev --reset-webhook`       | снять webhook, если он мешает локальной разработке |
| `pnpm dev --port 8788`           | другой порт                                        |
| `pnpm bot --whoami`              | узнать свой `OWNER_TELEGRAM_ID`                    |
| `pnpm bot --webhook https://...` | зарегистрировать webhook на задеплоенный воркер    |
| `pnpm bot --delete-webhook`      | снять webhook и вернуться к локальной разработке   |

Git-хуки (husky): **pre-commit** → `lint-staged` (ESLint --fix и Prettier по застейдженным),
**pre-push** → `pnpm check`.

## Создание ботов в BotFather

Нужны **два** бота: у бота ровно один webhook, поэтому делить токен между dev и production нельзя —
кто последним вызвал `setWebhook`, тот и забирает все апдейты.

**Dev-бот (делаем первым):**

1. В Telegram открыть [@BotFather](https://t.me/BotFather) → `/newbot`.
2. Отображаемое имя — любое, например `Dota Content Bot Dev`.
3. Username — глобально уникален и обязан заканчиваться на `bot`, например `dota_content_dev_bot`.
4. BotFather пришлёт токен → вписать в `.dev.vars` как `BOT_TOKEN` (файл в `.gitignore`).
5. Настройки бота открываются **Mini App** BotFather (кнопка Menu у строки ввода), в старом
   кнопочном меню нужного пункта нет. Там: бот → **Threads Settings** → включить **Threaded Mode**
   (это и есть темы в личном чате, поле `has_topics_enabled` в `getMe`). Возможность создавать темы
   пользователю не отключать — она нужна для `allows_users_to_create_topics`.
   При желании там же выключить добавление в группы: бот личный.
6. `pnpm bot` — проверит токен, выставит меню команд и скажет, включены ли темы.
7. Написать боту любое сообщение → `pnpm bot --whoami` → вписать свой id в `OWNER_TELEGRAM_ID`.

**Prod-бот:** те же шаги с другим именем и username. ⚠️ Его токен **не кладём в `.dev.vars`** —
только в секреты окружения:

```bash
pnpm exec wrangler secret put BOT_TOKEN --env production
BOT_TOKEN=<токен> pnpm bot   # меню команд для прод-бота
```

`OWNER_TELEGRAM_ID` у обоих один и тот же — это вы.

Git-хуки (husky): **pre-commit** → `lint-staged` (ESLint --fix и Prettier по застейдженным),
**pre-push** → `pnpm check`.

## Локальная разработка без Cloudflare

Логин в Cloudflare и публичный адрес для этого **не нужны**: `wrangler dev` поднимает воркер локально,
а D1 живёт файлом SQLite в `.wrangler/state/`.

Сложность одна: webhook — это push со стороны Telegram, а до `localhost` он достучаться не может.
Решает `pnpm dev`: он сам забирает апдейты (`getUpdates`, long polling — как это делает Telegraf)
и отдаёт их локальному воркеру тем же запросом и с тем же заголовком секрета, что прислал бы Telegram.
Обработчик разницы не видит, поэтому поведение совпадает с продом, где работает настоящий webhook.

Два терминала:

```bash
pnpm dev
```

Одна команда поднимает всё: применяет локальные миграции, запускает воркер и мост.
Вывод помечен префиксами `[worker]` и `[bot]`, Ctrl+C гасит оба процесса.
Дальше пишешь боту в Telegram и видишь ответ — правки кода `wrangler dev` подхватывает на лету.

⚠️ Запускать можно **только один** `pnpm dev` за раз: Telegram отдаёт `getUpdates` одному читателю,
а два воркера не поделят порт. Второй запуск мост распознает и скажет об этом.

- `getUpdates` несовместим с webhook: если он уже зарегистрирован, мост скажет об этом и предложит
  `pnpm dev --reset-webhook`.
- Без моста тоже можно — отправить воркеру фейковый апдейт curl'ом. Быстро проверяет логику
  (права, дедуп, ветвление команд) и вообще не трогает Telegram.
- Таймаут обработки поднят с дефолтных 10 секунд grammY до 50: первый вызов Bot API из нового
  изолята в 10 секунд регулярно не укладывался, и каждое первое сообщение после правки кода падало.
  50 секунд — ниже порога, после которого Telegram считает доставку неудачной.

## Если ответы приходят через 15 секунд

Симптом: в логах `bot api retry ... attempt: 1`, затем `reply sent ... ms: 15xxx`. То есть первый
вызов Bot API виснет до таймаута, а повтор проходит мгновенно.

Причина не в коде: **сломанный IPv6 в локальной сети**. Роутер его анонсирует, система берёт адрес,
а трафик не проходит. Node и curl спасает Happy Eyeballs — они пробуют оба протокола и берут тот,
что ответил. `workerd` так не умеет и честно ждёт таймаута на IPv6.

Проверка:

```bash
curl -4 -s -o /dev/null -m 8 -w "IPv4: %{http_code} за %{time_total}s\n" https://api.telegram.org/
curl -6 -s -o /dev/null -m 8 -w "IPv6: %{http_code} за %{time_total}s\n" https://api.telegram.org/
```

Если IPv4 отвечает за доли секунды, а IPv6 упирается в таймаут — отключить IPv6 на интерфейсе:

```bash
sudo networksetup -setv6off Wi-Fi        # вернуть обратно: -setv6automatic Wi-Fi
```

На задеплоенном воркере этой проблемы нет: у Cloudflare IPv6 рабочий. Повтор при сетевой ошибке
в коде остаётся — он нужен и в проде, но там срабатывает редко, а не на каждом сообщении.

## Секреты

`.dev.vars` (в `.gitignore`) копируется из `.dev.vars.example`:

| Переменная                | Значение                                         |
| ------------------------- | ------------------------------------------------ |
| `BOT_TOKEN`               | токен **отдельного тестового** бота из BotFather |
| `OWNER_TELEGRAM_ID`       | числовой Telegram ID владельца                   |
| `TELEGRAM_WEBHOOK_SECRET` | случайная строка ≥32 символов                    |

Генерация секрета — одинаково в обеих оболочках:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

⚠️ **Windows:** если PowerShell отказывается запускать `pnpm` («выполнение сценариев отключено»),
разово разреши их — `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` — либо вызывай `pnpm.cmd`.
Обходные конструкции вида `npx --yes pnpm@<версия>` в документации и скриптах не закрепляем.

В Cloudflare те же значения кладём через `wrangler secret put NAME --env dev`.
⚠️ dev и production используют **разных** ботов: у бота один webhook.
Токены не коммитим, не логируем и не передаём модели.

## Подключение Telegram

Локальный адрес Telegram недоступен — нужен публичный HTTPS Worker:

```bash
pnpm exec wrangler login
pnpm deploy:dev
pnpm exec wrangler secret put BOT_TOKEN --env dev
pnpm bot --webhook https://<worker>.workers.dev
```

Темы включаются в BotFather. Тот же код работает и в форум-супергруппе: ключ диалога —
`chat_id` + `message_thread_id`.

## Первая проверка

Webhook без настроенных секретов отвечает 503, с неверным секретом — 401.
После `/start` в личном чате бот отвечает в исходной теме, `/setup` заводит разделы.

Отдельного эндпоинта живости нет намеренно: Cloudflare воркер не опрашивает, а для личного бота
молчание в чате и есть признак поломки. Понадобится внешний мониторинг — добавим одной строкой.
