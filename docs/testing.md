# Тесты

## Как устроено

Тесты идут **внутри workerd** (`@cloudflare/vitest-plugin`), а не в Node с моками: та же среда,
те же биндинги, настоящая D1. Миграции применяются к тестовой базе перед файлом; `tests/setup.ts`
явно очищает таблицы перед каждым тестом. Плагин сам не изолирует D1 между тестами одного файла.
Проверки ESLint и локальных скриптов выполняются отдельно через Node (`scripts/tests/`).

```bash
pnpm test          # прогнать
pnpm check         # типы + линт + формат + тесты (он же на pre-push)
```

Исходящие вызовы перехватываются подменой глобального `fetch` (`tests/telegram-mock.ts`).
Перехват ловит **любой** запрос к `api.telegram.org` независимо от токена, а всё остальное роняет:
тест не должен незаметно сходить в сеть. Это не перестраховка — тестовый прогон подхватывает
настоящий `.dev.vars`.

## Что покрываем

Не проценты, а **список инвариантов**. Процентная планка здесь бессмысленна: она набирается
тестами на геттеры и ничего не говорит о том, отправится ли пост дважды.

Правило: **у каждого инварианта из списка есть тест. Список растёт вместе с фичами.**

| Инвариант                                                                            | Файл                                                |
| ------------------------------------------------------------------------------------ | --------------------------------------------------- |
| Webhook не пускает без секрета и с неверным секретом                                 | `tests/webhook.test.ts`                             |
| Чужой отправитель игнорируется и не отмечается в базе                                | `tests/webhook.test.ts`                             |
| Повторная доставка обрабатывается один раз                                           | `tests/webhook.test.ts`                             |
| Ответ уходит в ту же тему                                                            | `tests/webhook.test.ts`                             |
| При сбое вход сохраняется, ответ не-200, аренда восстанавливается                    | `tests/failure.test.ts`                             |
| Разделы создаются один раз и не дублируются                                          | `tests/sections.test.ts`                            |
| Команда раздела недоступна вне своих разделов                                        | `tests/commands.test.ts`                            |
| Владелец в группе не запускает личного бота; некорректный вход — 400                 | `tests/webhook.test.ts`                             |
| Гонка создания тем и отказ приветствия не создают дубль                              | `tests/sections.test.ts`, `tests/failure.test.ts`   |
| Неизвестный результат отправки не повторяется, успешный переиспользуется             | `tests/operations.test.ts`, `tests/failure.test.ts` |
| HTTP-повтор требует явной идемпотентности; Retry-After не сокращается                | `tests/http.test.ts`                                |
| Новые модули получают запрет импортов вбок и вверх, включая относительные реэкспорты | `scripts/tests/architecture.test.js`                |
| Локальная доставка не подтверждает неудавшийся апдейт и следующие за ним             | `scripts/tests/delivery.test.js`                    |

Что добавится обязательно: идемпотентность заданий, отсутствие двойной публикации, перенос
и отмена расписания, частичный успех площадок, удаление видео с проверкой активных задач.

## Что НЕ покрываем

- Чужие библиотеки: grammY, Drizzle, Hono. Их тестируют их авторы.
- Тексты сообщений: меняются часто, ломаются безопасно.
- Сам Telegram: его поведение проверяется вживую, а не моком.
- Геттеры, мапперы и прочий код без ветвлений.

## Как писать

1. **Тест на инвариант, а не на функцию.** Название — утверждение о поведении: «обрабатывает
   повторную доставку только один раз», а не «claimUpdate возвращает false».
2. **Интеграционно через `SELF.fetch`**, если путь проходит через вход: так проверяется вся цепочка
   вместе с middleware. Чистую логику (`isCommandAvailable`) тестируем напрямую.
3. **Проверяй состояние, а не только ответ.** Статус 200 ничего не значит, если в базе пусто.
4. Для модульных тестов транспорт передаём аргументом (`createHttpClient(url, { fetch })`).
   Интеграционные используют единый перехват `tests/telegram-mock.ts`: он обрабатывает Telegram
   и запрещает остальные внешние запросы. Произвольные глобальные подмены не добавляем.
5. Кэш на изоляте живёт между тестами одного файла. Состояние разделов в нём больше не хранится.
6. **Убедись, что тест умеет падать.** Сломай проверяемое поведение нарочно и посмотри на красный.
   Тест, который не падал ни разу, ничего не гарантирует.

## Приёмка

Изменение считается готовым, когда:

- [ ] `pnpm check` зелёный — включая тесты
- [ ] затронутый инвариант из списка покрыт тестом, а не «проверено руками»
- [ ] новый инвариант добавлен в таблицу выше
- [ ] тест видели красным хотя бы раз

Pre-commit запускает `lint-staged` для добавленных файлов, затем TypeScript и полный Prettier.
Коммит отменяется при ошибке. Pre-push запускает полный `pnpm check`: типы, линт, формат,
тесты, архитектурные проверки и проверку скиллов; его отчёт остаётся в терминале push.
Это не гарантия CI: серверного обязательного прогона пока нет.

После каждого шага `scripts/check.js` печатает `✅` или `❌`, длительность и итоговую сводку.
Полный вывод ошибки остаётся выше сводки, поэтому причину не нужно искать в другом логе.

## Что тесты уже нашли

Первый же прогон поймал два дефекта, которые прошли бы мимо любого чек-листа:

- `createForumTopic` с неожиданным ответом записывал `thread_id = null` — падало невнятной ошибкой
  SQL вместо понятного сообщения. Теперь ответ проверяется;
- `isAppError` опирался на `instanceof` и ломался при дублировании модуля — ошибка приложения
  превращалась в 500. Заменено на метку через `Symbol.for`;
- повторы в `lib/api.ts` были написаны и ни разу не выполнены: тест заставил вынести транспорт
  в аргумент, потому что иначе его не проверить.
