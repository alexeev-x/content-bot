# Восстановление после сбоя

Текущий бот работает только в личном чате `OWNER_TELEGRAM_ID`. Одна база обслуживает одного
бота и одного владельца. При смене токена или владельца нужна отдельная база: темы и журналы
относятся к конкретному чату. Группы намеренно не обслуживаются.

Вход сохраняется в `telegram_updates` до работы. `done` означает завершение, `processing` —
аренду на 120 секунд, `pending` — незавершённую работу. После истечения аренды повторная
доставка продолжает сценарий. Занятый или незавершённый апдейт получает не-2xx.

Исходящие операции сохраняются в `telegram_operations`. Успешный результат используется
повторно без обращения к Telegram. Явный отказ 429 сохраняет время следующей попытки.
Сеть, таймаут, 5xx, некорректный ответ или оборванное `sending` означают **неизвестный исход**:
автоматически повторять отправку нельзя. Telegram не предоставляет ключ идемпотентности
для этих методов; журнал не обещает exactly-once между Telegram и D1.

## Локальное восстановление

Останови локальный мост, запусти `pnpm dev --no-bot` на стандартном порту 8787. Скрипт ниже
работает только с локальной D1 окружения `dev`; удалённые базы он не меняет.

1. `pnpm recover list` — незавершённые апдейты и операции, без текстов сообщений.
2. Проверь результат в Telegram. Ключ `section:<chatId>:<sectionKey>:create` относится к созданию
   темы, `:intro` — к её приветствию. `update:<updateId>:<номер>:sendMessage` — к ответу на апдейт.
3. Если действие точно выполнено, запиши его настоящий идентификатор:
   - `pnpm recover resolve <key> --thread-id <id>` для создания темы;
   - `pnpm recover resolve <key> --message-id <id>` для сообщения.
4. Только если проверка подтвердила, что действия **не было**, разреши новую попытку:
   `pnpm recover resolve <key> --not-sent`. Это также подходит после устранения причины
   явного отказа 400/403. При сомнении оставь операцию заблокированной.
5. `pnpm recover retry <update_id>` повторно доставит сохранённый вход локальному воркеру.
   После успеха можно вернуть обычный `pnpm dev`.

Скрипт не определяет отсутствие сообщения за владельца. В Bot API нет метода получения всех
тем; иногда для сверки ID нужен клиент Telegram. Если ID неизвестен, не подставляй случайный.
Активное `sending` скрипт менять не разрешает, а изменение состояния проверяет атомарно.

Удаление темы через `pnpm bot --delete-topic` удаляет сообщения в Telegram, но не её запись
в D1. Это обслуживание, а не штатный сценарий: `/setup` не обещает восстановление. Для новой
темы нужно согласованно обновить запись раздела и его операции; не очищай всю базу при живых
темах — это создаст дубли.

## Ограничения текущего этапа

Автоматического фонового добора пока нет. Обычно повтор доставляет Telegram либо локальный
мост; Telegram не хранит апдейты бесконечно. После прекращения доставки вход остаётся в D1,
его можно восстановить описанным способом. Перед первым продакшен-деплоем нужны удалённый
процесс восстановления, мониторинг незавершённых операций и политика хранения журналов.
Не удаляй журнал разделов и незавершённые записи: они защищают от повторных эффектов.
