# content-bot — архитектура

Личный Telegram-бот для контента о Dota 2: идеи, рубрики, тексты и сценарии с памятью об авторском
стиле, публикация готовых материалов в Telegram, позже — YouTube и TikTok.
**Hono + grammY на Cloudflare Workers (Free), D1 как источник истины.**

Этот файл — архитектура приложения, её правила и ограничения. Единственный источник правды по
устройству кода: при расхождении с любым другим документом выигрывает он.

| Файл                           | О чём                                                        |
| ------------------------------ | ------------------------------------------------------------ |
| `AGENTS.md`                    | Инструкция для ИИ-агентов: с чего начать, команды, процесс   |
| `docs/setup.md`                | Установка, секреты, подключение Telegram                     |
| `docs/publishing-and-media.md` | Публикации и видео: загрузка, площадки, хранение             |
| `docs/bot-plan.md`             | Продукт: сценарии, разделы бота, этапы, критерии готовности  |
| `docs/decisions.md`            | Принятые решения, отклонённые альтернативы, открытые вопросы |

> **Статус: каркас работает локально.** Есть вход (webhook, доступ владельца, дедуп апдейтов),
> разделы бота в `core/sections`, журнал операций Telegram, D1 с миграциями из схемы и тесты внутри workerd.
> Продуктовых фич ещё нет — `src/modules/` пуста. Деплой ни разу не выполнялся: в `wrangler.jsonc`
> заглушки вместо `database_id`. Разделы про этапы 2–3 описывают целевое устройство.

Работаем только с локальным dev-ботом. Прод-бот — после реализации хотя бы 2–3 основных разделов.

### Надёжность текущего каркаса

`app/telegram` сохраняет исходный апдейт и аренду обработки в D1. Только `done` подтверждается
как обработанный дубль. После сбоя вход остаётся доступен для повторной доставки.
`core/telegram` ведёт журнал исходящих действий: подтверждённый результат переиспользуется,
неизвестный исход требует сверки. Создание темы и её приветствие имеют разные стабильные ключи;
тема сохраняется до отправки приветствия. Глобального флага «всё создано» нет.

Транспорт повторяет запрос только с явной гарантией `idempotent: true`; изменяющие методы Telegram
не повторяются внутри HTTP-клиента. Для 429 время следующей попытки сохраняется в журнале.
Автоматического фонового добора пока нет: восстановление локальной работы — `pnpm recover`,
процедура и ограничения описаны в [docs/recovery.md](docs/recovery.md).

Для обычного `/start` с созданным разделом: около 8 запросов к D1 и 1 внешней отправки;
создание каждого недостающего раздела добавляет до 6 запросов D1 и 2 внешних вызова. Это оценка по коду,
а не замер CPU. Работу с реальными задержками dev-бота проверяем отдельно от тестов.

## Стек

- **TypeScript strict**, ES modules. **pnpm** + единый lockfile.
- **Hono** — HTTP: Telegram webhook, OAuth-коллбэки площадок.
- **grammY** — разбор апдейтов и маршрутизация команд. Живёт **только** в `app/telegram`.
- **Zod** — валидация всего, что пришло снаружи. `@hono/zod-openapi` + Swagger UI добавляем
  **только** когда появится собственный HTTP API (Mini App), для одного webhook они не нужны.
- **Cloudflare Workers Free** (`wrangler`), биндинги по мере появления: `DB` (D1), `JOBS` (Queues),
  `SCHEDULER` (Durable Object), `BUCKET` (R2, этап видео), `CACHE` (KV, только если докажем нужду).
- **D1** — источник истины. Миграции — SQL-файлы, применяются Wrangler'ом.
- **ESLint** (flat config) + **Prettier** + **husky/lint-staged**. ESLint держит не стиль (это дело
  Prettier), а правила архитектуры: границы слоёв, запрет импортов вбок, `type` вместо `interface`.

Node.js — только локальный инструмент. В продакшене рантайм Workers: нет процесса, диска и произвольных
Node-пакетов; совместимость проверяем для конкретной зависимости и `compatibility_date`.

## Архитектура (Vertical Slice — по фичам)

Модульный монолит, один Worker. Группируем **по фиче**, не по слою: фича = папка в `src/modules/`.
Добавить функционал — добавить папку, удалить — удалить папку. Пустые слои и папки заранее не создаём.

**Вход и фичи разведены.** `app/` — это как приложение принимает работу: webhook, доступ владельца,
защита от повторной доставки, очередь, cron. Удалить это нельзя, фичей оно не является.
`modules/` — только фичи: каждая живёт своей папкой и не знает, кто её позвал — Telegram, очередь
или cron. Сервисы не получают `Context` Hono или grammY — только обычные данные и явные зависимости.
Внутреннюю логику не запускаем через искусственный `app.fetch()`. DI-контейнер не нужен.

```text
src/
  index.ts              # composition root: связывает вход и фичи, export fetch/queue/scheduled + DO
  app/                  # ВХОД в приложение. Не фича — удалить нельзя
    telegram/           # webhook, доступ владельца, дедуп апдейтов, разбор и маршрутизация команд
    middleware/         # error.ts  logger.ts  telegram-auth.ts
    config.ts           # разбор и проверка секретов воркера
    queue.ts            # queue(): сообщение -> job -> обработчик          (этап 2)
    cron.ts             # scheduled(): добор просроченного, ретрай outbox  (этап 2)
  modules/              # ТОЛЬКО фичи
    conversations/      # сообщения темы, текущий материал и версия
    editor/             # оркестрация: rubrics + memory + materials -> вызов модели
    rubrics/            # правила и настройки рубрик
    materials/          # материалы, версии, одобрение, источники
    memory/             # правила стиля, замечания, подбор примеров
    publishing/         # аккаунты, публикации, время, статусы площадок
      index.ts          #   монтаж + контракт; общее для слайсов в корне модуля
      channel/ youtube/ tiktok/   # слайс = controller.ts + service.ts + свой upstream.ts
    media/              # видео: загрузка в R2, ключ, размер, срок удаления
  core/                 # ДОМЕННОЕ ядро, общее для фич (не утилиты и не фича)
    sections/           # общий механизм тем и сопоставления section_key ↔ thread_id
    telegram/           # транспорт Bot API и журнал его операций; без команд и текстов
    ai/                 # клиент модели + адаптер поставщика
    jobs/               # выдача/захват заданий, попытки, backoff, outbox
    scheduler/          # Durable Object: alarm'ы расписания и локи материала
  lib/                  # МЕЛКИЕ domain-agnostic утилиты
    api.ts              # HTTP-клиент: таймаут, явная безопасность повторов, -> AppError
    errors.ts           # AppError: code + retryable. Про HTTP не знает
    router.ts  logger.ts
  types/                # общие типы: env.ts, bot.ts
  const/                # каталоги, общие для входа и фич: commands.ts
migrations/             # SQL, сгенерированный из table.ts (pnpm db:generate)
```

⚠️ **Данные фичи живут в самой фиче.** Определения разделов — `modules/<owner>/sections.ts`.
Пока продуктовых модулей нет, стартовый каталог находится в `core/sections/catalog.ts`.
Общий механизм тем остаётся в `core/sections`. В `const/` попадает только то,
что нужно и входу, и фичам одновременно (имена команд), а в `types/` — контракты между ними
(`BotCommand`). Общие zod-схемы заведём в `src/schemas/`, когда появится вторая сторона:
схема окружения её не имеет и потому лежит в `app/config.ts`.

### Слои и направление зависимостей

Слои строгие: **импорт только вниз, и никогда вбок**.

```
src/index.ts              composition root — единственное место, где вход и фичи знают друг о друге
      │ собирает и связывает
      ├──────────────┐
      ▼              ▼
app/            modules/     друг друга НЕ видят ни в ту, ни в другую сторону
      └──────┬───────┘
             ▼
core/                        доменное ядро. Ни о входе, ни о фичах не знает
             ▼
lib/                         утилиты. Ни о домене, ни о фичах не знает
             ▼
types/ schemas/ const/       уровень 0: импортируются откуда угодно, сами не импортируют ничего
```

| Откуда      | Куда можно                           | Куда нельзя                                      |
| ----------- | ------------------------------------ | ------------------------------------------------ |
| `index.ts`  | всё                                  | —                                                |
| `app/*`     | `core`, `lib`, уровень 0, свои файлы | **`modules/*`**, `index.ts`                      |
| `modules/X` | `core`, `lib`, уровень 0, свои файлы | **`modules/Y`** (сосед), **`app/*`**, `index.ts` |
| `core`      | `lib`, уровень 0, свои файлы         | `modules/*`, `app/*`, `index.ts`                 |
| `lib`       | уровень 0, свои файлы                | `core`, `modules/*`, `app/*`, `index.ts`         |
| уровень 0   | ничего                               | всё остальное                                    |

Почему фича не видит вход: её должно быть можно поднять из очереди и cron, а не только из Telegram.
Почему вход не видит фичу: иначе `app` пришлось бы править при каждой новой фиче.

- **`lib/`** — мелкое, domain-agnostic и переиспользуемое. Ничего «сверху» не импортирует **и не
  реэкспортирует**: реэкспорт типа из `core` или модуля делает `lib` зависимым от домена окольным
  путём. Крупные доменные подсистемы сюда не кладём.
  `lib/api.ts` — фабрика `createHttpClient` (хост, таймаут, явно разрешённые повторы, ошибки → `AppError`).
- **`core/`** — доменное ядро для нескольких фич. Наружу — самодостаточные функции
  (`enqueueJob`, `claimDueJobs`, `getScheduler`), низкоуровневое внутри.
  Внешний клиент, нужный **нескольким** модулям, живёт здесь (`core/telegram/`, `core/ai/`):
  он часть домена, а не утилита, и не принадлежит ни одной фиче. Модули импортируют `core`
  напрямую — порты нужны только между модулями.
- **Клиент, нужный одному модулю или слайсу, — `upstream.ts` рядом с его `service.ts`**
  (`publishing/youtube/upstream.ts`). Использует `createHttpClient`, проверяет внешний ответ через zod;
  маппинг в наш тип — внутри адаптера. ❌ Сырой контракт площадки наружу модуля не течёт.
- ❌ Циклы недопустимы. Внутри модуля импортируем конкретные файлы, а не собственный `index.ts`.

### Как модули работают друг с другом

`import { saveVersion } from 'src/modules/materials'` внутри другого модуля — **ошибка**, даже через
публичный `index.ts`. Иначе слой «модули» превращается в клубок, и удалить фичу удалением папки
перестаёт получаться.

Вместо этого модуль **объявляет порт — тип того, что ему нужно**, и получает зависимость аргументом:

```ts
// modules/editor/service.ts — потребитель описывает СВОЙ минимальный контракт
type Deps = {
  getRubric: (id: RubricId) => Promise<Rubric>;
  saveVersion: (input: NewVersion) => Promise<VersionId>;
};

export const composeDraft = async (input: DraftInput, deps: Deps) => {
  /* ... */
};
```

```ts
// src/index.ts — composition root: единственное место, где фичи встречаются
const editor = createEditor({ getRubric: rubrics.getRubric, saveVersion: materials.saveVersion });
```

Тип зависимости описывает **потребитель**, а не владелец: структурная типизация TypeScript сведёт их
в `index.ts` без единого импорта между модулями. Заодно сервис становится проверяемым без всей сборки.

Когда двум модулям нужно одно и то же, есть ровно три законных исхода:

1. **Общее опускается в `core/`** — если это доменная механика (задания, транспорт Telegram, ИИ).
2. **Связь поднимается в оркестратор** — сценарий, который ходит в несколько модулей, живёт в `editor`
   и получает их порты аргументами. Обратных зависимостей на `editor` нет ни у кого.
3. **Данные читаются через порт владельца** — чужую таблицу не трогаем: ни `queries.ts` соседа,
   ни его SQL. Нужен JOIN — специализированный запрос пишет **владелец** данных и отдаёт готовый тип.

Проверяется механически — правилом `import/no-restricted-paths` в `eslint.config.mjs`. Зоны на слои
заданы явно, а зона «не импортируй соседа» **генерируется из списка папок `src/modules/`**: новый
модуль получает защиту сам, без правки конфига. Ловятся оба написания — и `src/modules/...`,
и обход через `../`, потому что путь резолвится, а не сравнивается как строка.
Ошибка видна прямо в редакторе, а не только на pre-push.

### Устройство фичи

**Канон обязателен для `modules/`.** Открыв любую фичу, видишь одно и то же — угадывать не нужно.

```text
modules/materials/        # файлы БЕЗ префикса фичи — папка уже namespace
  index.ts       публичный контракт: что видит composition root. Здесь можно писать код,
                 а не только реэкспортировать
  service.ts     логика и сценарии. Зависимости приходят аргументами
  queries.ts     запросы к своим таблицам
  table.ts       схема таблиц (из неё drizzle-kit генерирует миграцию)
  schema.ts      zod-схемы внешних данных
  types.ts       типы фичи, не выводимые из schema и table
  commands.ts    команды бота этой фичи: BotCommand[]
  sections.ts    разделы фичи: SectionDefinition[] — если у неё есть своя тема в чате
  upstream.ts    клиент внешнего API, нужный только этой фиче
```

Заводим только те файлы, что реально нужны, — но **называем всегда так**. Пустых посредников нет.

| Файл          | Отвечает за                                | Знает про Hono/grammY? |
| ------------- | ------------------------------------------ | ---------------------- |
| `index.ts`    | публичный контракт, при нужде — код сборки | нет                    |
| `service.ts`  | логика, порядок шагов, бросает `AppError`  | нет                    |
| `queries.ts`  | чтение и запись своих таблиц               | нет                    |
| `table.ts`    | форма данных в БД                          | нет                    |
| `schema.ts`   | форма внешних данных                       | нет                    |
| `types.ts`    | остальные типы фичи                        | нет                    |
| `commands.ts` | команды бота этой фичи                     | нет                    |
| `sections.ts` | разделы, которыми фича владеет             | нет                    |
| `upstream.ts` | внешний API только этой фичи               | нет                    |

⚠️ **`core/` и `app/` этому канону НЕ подчиняются.** Это общая инфраструктура и вход — они не обязаны
иметь полный набор ролей.

- Хватает одного файла — пусть будет один файл: `core/telegram.ts`.
- Есть своя таблица и логика — появляется папка: `core/sections/` с `table.ts`, `queries.ts`,
  `service.ts`, `index.ts`.
- `app/telegram/` — вход со своими правилами: `bot.ts`, `controller.ts`, `queries.ts`, `table.ts`,
  `types.ts`, `index.ts`. Роли те же по смыслу, но полный набор не требуется.

Правило одно: **лишних файлов нет нигде, обязательный канон — только в фичах.**

❌ `controller.ts` — это **набор функций, а не класс**: классовый контроллер ломает вывод типов в Hono.
❌ `utils.ts` как свалка: осмысленный кусок получает файл по имени (`rules.ts`, `retry.ts`).

### Как фича растёт

Ступеньками, не перепрыгивая. Пустых папок заранее не создаём.

**1. Плоский модуль** — норма, так выглядит большинство фич.

**2. Разрослась одна роль** → она становится папкой с ТЕМ ЖЕ именем и `index.ts` внутри
(`service.ts` → `service/index.ts`). Импорт `from './service'` резолвится и в файл, и в папку,
поэтому переход ничего не ломает. Обратное тоже верно: папка с одним `index.ts` — лишний уровень,
такую сворачиваем обратно в файл (так `core/telegram/index.ts` стал `core/telegram.ts`).

**3. В модуле два несвязанных ресурса** → режем на под-слайсы. Слайс = папка со своими
`controller.ts` и `service.ts`; общее для слайсов (`table.ts`, `schema/`, `types/`, `upstream.ts`)
поднимается в корень модуля:

```text
modules/publishing/
  index.ts              только монтаж и публичный контракт
  table.ts              общие таблицы модуля
  channel/    index.ts controller.ts service.ts
  youtube/    index.ts controller.ts service.ts upstream.ts
  tiktok/     index.ts controller.ts service.ts upstream.ts
```

### Где живут schema и types

- **zod-схема** — ровно два места: в модуле (`schema.ts` / `schema/<тема>.ts`) **ИЛИ** в `src/schemas/`
  (если нужна ≥2 модулям).
- **тип** — так же: в модуле **ИЛИ** в `src/types/` (общий: `Env`, `Job`, идентификаторы).
- ❌ Не заводим `schema.ts`/`types.ts` в `core/` и `lib/` — там логика, общее берут из `src/schemas`, `src/types`.
- Локальный неэкспортируемый тип можно оставить в файле.

## Модули и владение данными

| Модуль          | Данные и ответственность                                                |
| --------------- | ----------------------------------------------------------------------- |
| `telegram`      | webhook, проверка владельца, команды, тексты ответов                    |
| `sections`      | разделы бота: соответствие «раздел ↔ тема Telegram»                     |
| `conversations` | сообщения темы, выбранный материал и версия                             |
| `rubrics`       | правила и настройки рубрики                                             |
| `materials`     | материал, версии, одобрение, источники                                  |
| `memory`        | правила стиля, замечания, подбор одобренных примеров                    |
| `editor`        | координация `rubrics` + `materials` + `memory`, сборка контекста модели |
| `publishing`    | подключённые аккаунты, записи публикаций, время, статусы площадок       |
| `media`         | ключ R2, размер, связи файла, срок удаления                             |
| `core/jobs`     | состояние заданий, попытки, локи, outbox                                |

- Модуль ходит в чужие данные **только** через порт, полученный аргументом из `src/index.ts`,
  и никогда через импорт соседа или его `queries.ts`.
- **Продуктовые команды принадлежат модулю-владельцу** (`modules/rubrics/commands.ts`), а не входу: удалить
  папку фичи — значит убрать и её команды. Вход получает готовый список `BotCommand` и регистрирует.
- Обратных зависимостей на `editor` нет: он координирует, его не зовут.
- `core/jobs` не знает обработчиков конкретных фич — реестр передаётся при сборке.
- Одобренный текст живёт в `materials`; `memory` ссылается на него, копии не делает.
- Бинарное видео — в R2, метаданные — в D1.
- Чтение через JOIN допустимо, запись чужих данных — только через сервис владельца.
  Интерактивных транзакций в D1 нет: атомарность — через batch или один UPDATE с условием.

## Диалог и контекст

- Ключ диалога = `chat_id` + `message_thread_id`. Один `thread_id` ключом **не является**.
  Личность владельца проверяется отдельно, по Telegram user ID.
- Темы в личном чате с ботом — поддерживаются Bot API (`has_topics_enabled`,
  `allows_users_to_create_topics`, `message_thread_id` для приватных чатов), включаются в BotFather.
  Текущий вход допускает только личный чат владельца. Для форум-супергруппы потребуется
  отдельное решение доступа и ключи `(chat_id, thread_id)` в хранилище разделов.
- Разделы бота — темы, которые создаёт **сам бот** (`/setup`). Пользователю создание и удаление тем
  запрещено настройкой в BotFather, поэтому раздел нельзя потерять случайно. Соответствие
  «раздел ↔ `thread_id`» живёт в D1: по нему определяется, в каком разделе идёт разговор.
  Закрепить тему или задать порядок Bot API не позволяет — разделы различаем цветом иконки.
- Для каждой темы храним выбранный материал и версию. Перед изменением сверяем актуальную версию,
  чтобы параллельная задача не перезаписала результат. При неоднозначной команде — уточняем.
- Один материал открывается в разных темах без копирования.
- ❌ Глобальные переменные Worker — не память диалога. Состояние только в D1 (или в DO-сторидже).

## Сборка контекста для модели

Перед генерацией собираем ограниченный контекст: общие правила канала → правила рубрики →
подходящие одобренные примеры → текущий текст и запрос автора → источники с датой при проверке фактов.
Архив целиком модели не отправляется: фильтры + текстовый поиск по D1; векторное хранилище —
не обязательная зависимость.

Модель возвращает текст **или** структурированное действие. Код проверяет схемой права, состояние и
допустимость. Модель не получает токены, произвольный SQL и возможность публиковать в обход сервисов.

Различаем и не смешиваем: «одобрено» (сохранить версию, **не публиковать**), «запомни правило»
(обновить память), «здесь убери шутку» (правка одного материала), «публикуй» (отправка).
Загруженное видео или чужой текст образцом авторского стиля автоматически не становятся.

## Задания, расписание и идемпотентность

Ниже — целевая схема этапа 2. Текущий inbox и журнал Telegram описаны выше; `core/jobs`,
очередь и расписание ещё не реализованы.

Источник истины по заданиям — **D1**, не очередь. Очередь и alarm — только транспорт исполнения.

1. Webhook проверяет секрет и владельца, пишет `update_id` для дедупа и задание в D1,
   после надёжной записи отвечает Telegram. Генерация идёт отдельно.
2. Таблица **outbox** связывает запись в D1 с постановкой в Queues: не удалось положить в очередь —
   повторим из cron. Так частичный сбой не теряет работу.
3. В сообщении очереди — **job ID и версия формата**, никакого содержимого и тем более видео.
4. Каждое задание: уникальный ID, тип, состояние, число попыток, время следующей попытки.
5. Queues доставляет повторно и вне порядка → обработчик идемпотентен, захват задания атомарен
   (`UPDATE ... WHERE state='pending'` с ограниченным сроком лока), результат пишется до `ack`.
6. Изменения одного материала сериализуем: DO на материал/диалог либо проверка версии.
7. Временные ошибки — ограниченный ретрай с backoff; постоянные — конечный статус и понятное сообщение
   владельцу. Для 429 уважаем `Retry-After` площадки. ❌ Долгих `sleep`: храним время следующей попытки.

**Не завязывать этап 1 жёстко на Queues.** Free-квота 10 000 операций в день и хранение 24 часа,
одна задача расходует несколько операций. `core/jobs` предоставляет интерфейс «поставить задание»,
драйверов два: очередь (когда включена) и добор из D1 по alarm/cron. Смена драйвера не трогает фичи.

**Расписание.** Время храним в UTC, показываем в часовом поясе владельца. Наступившие задачи выбирает
**Durable Object с alarm** (`core/scheduler`): он же даёт сериализацию и лок. Cron остаётся страховкой —
подбирает просроченное, если alarm не сработал, ретраит outbox и запускает ежедневную очистку.
Минутный cron сам по себе не даёт секундной точности, и alarm её тоже не гарантирует — точность
до секунды не обещаем.

DO доступен на Free с SQLite-бэкендом (1 ГБ на объект, 5 ГБ на аккаунт), так что это не платная зависимость.

Запись в D1 и внешняя публикация — не одна транзакция. Неопределённый результат отправки: сначала
проверяем статус у площадки; где проверки или идемпотентности нет — задача получает статус
«неопределённо» и ждёт решения владельца. ❌ Повтор вслепую запрещён.

## Публикации и видео

Одна запись публикации = одна площадка + один аккаунт. Она закрепляет конкретную версию материала,
описание, файл и время. Правка черновика её не меняет без отдельной команды. Одобрение материала и
статус публикации — разные состояния: YouTube может быть опубликован, пока TikTok в ошибке.
Успех на одной площадке не повторяется из-за ошибки другой.

Ролик весит 200–250 МБ и **через бота не забирается** (`getFile` отдаёт максимум 20 МБ), поэтому для
YouTube и TikTok файл попадает в R2 мимо Telegram, а в Telegram-канал уходит пересылкой по `file_id`.
Полный разбор — ограничения Telegram, загрузка через Mini App, resumable-выгрузка на площадки,
сроки хранения — в **`docs/publishing-and-media.md`**.

## Платформенные лимиты (Free)

Проверено 19 сентября 2026 по документации Cloudflare. Квоты общие на аккаунт — перед деплоем
смотрим фактический остаток, на аккаунте уже живут другие воркеры.

| Лимит                         | Значение                                        | Что из этого следует                                              |
| ----------------------------- | ----------------------------------------------- | ----------------------------------------------------------------- |
| Workers Free: запросы         | 100 000/день                                    | хватает; cron раз в минуту — это 1440/день                        |
| Workers Free: CPU             | **10 мс на вызов**                              | ожидание сети не CPU. Мерить реальный разбор апдейта grammY + zod |
| Workers Free: **subrequests** | **50 на вызов**                                 | бюджет на вызовы модели + Telegram в одном обработчике            |
| Тело запроса (Free-аккаунт)   | **100 МБ**                                      | видео крупнее — только multipart                                  |
| D1 Free                       | 5 млн чтений / 100 тыс. записей в день, 5 ГБ    | основное хранилище; индексы и выборки с лимитом                   |
| Queues Free                   | 10 000 операций/день, retention 24 ч            | долговременное состояние — в D1, очередь опциональна              |
| Durable Objects Free          | только SQLite-бэкенд, 1 ГБ/объект, 5 ГБ/аккаунт | alarm'ы и локи бесплатны                                          |
| KV Free                       | 100 тыс. чтений / 1000 записей в день           | только необязательный кэш                                         |
| R2                            | 10 ГБ-месяц, 1 млн A / 10 млн B операций        | отдельная подписка с оплатой превышения                           |
| Workers AI                    | 10 000 Neurons/день (проверить)                 | Neurons — единицы вычислений, не сообщения; часть моделей платная |

- **KV не годится** для локов, защиты от дублей и немедленного чтения только что записанного:
  изменения распространяются с задержкой. Актуальные правила, версии и статусы — только D1.
- При исчерпании квоты соответствующая функция **останавливается с уведомлением**;
  автоматического перехода на платный тариф нет.
- R2 — отдельная подписка, Workers Free не блокирует начисления при превышении. Подключаем только
  после явного согласия владельца; до этого этап видео не начинаем.
- Полностью бесплатный ИИ — главный риск качества: бесплатные модели Workers AI по-русски в авторском
  стиле пишут посредственно, а 10 000 Neurons/день для длинных текстов мало. Адаптер держим сменяемым,
  выбор поставщика — отдельное решение владельца по бюджету.

## Биндинги и env

Деплой **всегда с явным окружением** (`--env dev` / `--env production`). Верхний уровень — база,
напрямую не деплоится. dev и production — **разные** боты, базы, очереди и DO.

⚠️ Наследование в `wrangler.jsonc`: `main`, `compatibility_date`, `compatibility_flags`, `account_id`,
`migrations` наследуются и держатся **один раз сверху**; **биндинги не наследуются** —
`vars`, `d1_databases`, `kv_namespaces`, `r2_buckets`, `queues`, `durable_objects`, `triggers`
дублируем в **каждый** env, иначе wrangler напишет «is not inherited by environments» и биндинга не будет.

- Биндинги добавляем **по мере появления функции**, спекулятивных нет.
- **После любой правки `wrangler.jsonc` → `pnpm cf-typegen`.** `worker-configuration.d.ts` генерируемый,
  руками не редактируем, в git не держим.
- Секреты — `wrangler secret put NAME --env <env>`, никогда не в `vars`.
  Локально — `.dev.vars` (в `.gitignore`), рядом `.dev.vars.example` с пустыми полями.
  Минимум: `BOT_TOKEN`, `OWNER_TELEGRAM_ID`, `TELEGRAM_WEBHOOK_SECRET` (≥32 символа).
- ⚠️ Один Telegram-токен нельзя делить между dev и production: у бота один webhook. Для dev — отдельный бот.
- OAuth-токены площадок храним зашифрованными, ключ шифрования — в Secrets.

## Ошибки, секреты и логирование

- Единый `AppError { code, message, retryable }`. HTTP-слой переводит его в статус, Telegram — в текст
  для владельца, очередь — в решение о повторе. ❌ Голый `throw new Error` наружу.
- Логируем: request ID, job ID, material ID, publication ID, тип действия, длительность, код ошибки.
- ❌ Никогда не логируем и не отдаём модели: токены, заголовки авторизации, подписанные URL,
  полные сообщения автора, сырые тела ответов ИИ.

## Конвенции

- **Только `type`, без `interface`.** Функции-хелперы — стрелочные (`export const fn = () => {}`).
- Внешние данные — сначала `unknown`, затем zod. Типы выводим через `z.infer`, руками не дублируем.
  Обоснованный `any` — комментарием, почему.
- **Имена:** папки kebab-case; файлы внутри модуля — по роли (`service.ts`), без префикса фичи.
- **Порядок в файле:** типы → константы → экспортируемые функции → внутренние хелперы.
- **Импорты:** кросс-модульное — абсолютом от `src/` (`import { AppError } from 'src/lib/errors'`,
  alias `src/*` в `tsconfig.json`); сиблинги — относительным `./`.
- **Кроссплатформенность.** Код и скрипты работают и на macOS, и на Windows: в `package.json` только
  `node` и бинарники из `node_modules`, вспомогательные шаги — `scripts/*.js`, переносы строк LF.
  Подробности — `docs/setup.md`.
- Миграции версионируются, применённые не переписываются.
- Зависимость добавляем под конкретную задачу. Пустые абстракции и «универсальные базовые сервисы»
  заранее не создаём; общую схему выносим только при реальном совпадении смысла.
- Тесты идут внутри workerd с настоящей D1 и входят в `pnpm check`. Покрываем инварианты,
  а не проценты — список в `docs/testing.md`.

## Как добавить фичу

Механически, за пять шагов. Трогаем ровно три файла снаружи папки фичи.

**1. Папка фичи** `src/modules/<feature>/` — только нужные роли:

```text
table.ts       таблицы фичи        -> pnpm db:generate сгенерирует миграцию
queries.ts     запросы к своим таблицам
service.ts     логика; зависимости (d1, core-клиенты, порты соседей) приходят аргументами
commands.ts    команды бота этой фичи: BotCommand[]
sections.ts    разделы фичи: SectionDefinition[] — если у неё есть своя тема в чате
index.ts       публичный контракт: что видит composition root
```

**Раздел принадлежит фиче, как и команды.** Но связь не «один к одному»: у `editor` и `memory`
по одному разделу, у `publishing` два (по слайсу на площадку), у `rubrics` — по разделу на рубрику
и набор меняется на ходу, а у `materials`, `conversations` и `media` разделов нет вовсе — это
данные, а не поверхность общения. Поэтому `core/sections` — не владелец списка, а **реестр**:
он создаёт темы, помнит соответствие «раздел ↔ `thread_id`» и отвечает, где идёт разговор.

**2. Имена команд** — в `src/const/commands.ts`: добавить в `command` и, если команда нужна
пользователю в меню, в `menuCommands`. Там же указывается, где команда работает:

```ts
{ name: command.approve, description: 'Одобрить версию', sections: ['editor', 'telegram-posts'] }
```

Без поля `sections` команда доступна везде. После правки `pnpm bot` обновит меню в Telegram.

⚠️ Меню в интерфейсе Telegram **одно на чат**: у `setMyCommands` есть scope на чат, участника и
админов, но не на тему. Поэтому команда чужого раздела в меню видна, но вход её не выполнит —
ответит, где она работает. В `/help` показываются только доступные здесь.

**3. Связывание** — в `src/index.ts`: создать сервис, добавить его команды и разделы в списки.

```ts
const sections = createSections({ d1: env.DB, telegram, catalog: [...editorSections, ...publishingSections] });
const materials = createMaterials({ d1: env.DB, telegram });

return {
  telegram,
  sections,
  commands: [...createSectionCommands({ telegram, sections }), ...createMaterialCommands({ telegram, materials })],
};
```

**4. Если вход должен что-то знать о фиче** (например, показывать её в справке) — добавить метод
в `src/app/telegram/types.ts`. Порт описывает **потребитель**: структурная типизация сама сведёт
его с реализацией в `index.ts`, импортов между `app` и `modules` не появится.

**5. Проверить**: `pnpm db:generate` (если менялись таблицы) и `pnpm check`.

❌ Чего делать не нужно: править `app/telegram` при добавлении фичи, импортировать соседний модуль,
складывать данные фичи в `const/`, заводить пустые файлы «на будущее».

## Инварианты (Do / Don't)

- ✅ D1 — источник истины по заданиям и расписанию. ❌ Очередь как единственное хранилище состояния.
- ✅ Обработчики идемпотентны, захват задания атомарен. ❌ Повтор вслепую при неизвестном результате.
- ✅ grammY только в `app/telegram`, транспорт Bot API — в `core/telegram.ts`. ❌ `Context` в сервисах.
- ✅ Логика в `service`, тонкий хендлер сверху. ❌ Бизнес-логика в роуте или в команде.
- ✅ Все ошибки через `AppError`. ❌ Сырой текст провайдера владельцу.
- ✅ Видео — напрямую в R2. ❌ Файл через `getFile` и в память Worker.
- ✅ «Одобрено» ничего не публикует. ❌ Разовая правка, ставшая постоянным правилом.
- ✅ Модули связываются только в `src/index.ts` через порты. ❌ Импорт соседнего модуля — даже его `index.ts`.
- ✅ `lib` ничего не знает о домене. ❌ Реэкспорт из `core`/`modules` внутри `lib`.
- ✅ Общее у двух модулей опускается в `core` или поднимается в оркестратор. ❌ «Просто импортну соседа».
