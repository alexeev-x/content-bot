# content-bot — архитектура

Приложение на **Cloudflare Workers (Free)**, HTTP-слой — **Hono**.

Этот файл — архитектура приложения, её правила и ограничения. Единственный источник правды по
устройству кода: при расхождении с любым другим документом выигрывает он.

| Файл                | О чём                                                      |
| ------------------- | ---------------------------------------------------------- |
| `AGENTS.md`         | Инструкция для ИИ-агентов: с чего начать, команды, процесс |
| `docs/setup.md`     | Установка, локальный запуск, деплой                        |
| `docs/practices.md` | Инженерные правила: типы, асинхронность, ошибки, логи      |
| `docs/testing.md`   | Что покрываем тестами и когда изменение считается готовым  |
| `docs/skills/*.md`  | Скилы для агентов: архитектура, стек, приёмка              |

> **Состояние: чистый лист.** В репозитории есть воркер, который поднимается и отвечает 404 на любой
> путь, контракт ошибок, логи и вся оснастка проверок. Функциональности нет никакой: ни входов,
> ни фич, ни хранилища, ни биндингов, ни секретов. Деплой ни разу не выполнялся.
>
> Архитектуру собираем с нуля. Правила ниже — то, по чему она будет собираться.

## Стек

- **TypeScript strict**, ES modules. **pnpm** + единый lockfile.
- **Hono** — HTTP-слой воркера.
- **Cloudflare Workers Free** (`wrangler`). Биндингов нет.
- **Vitest внутри workerd** (`@cloudflare/vitest-plugin`) — тесты в той же среде, что и прод.
- **ESLint** (flat config) + **Prettier** + **husky/lint-staged**. ESLint держит не стиль (это дело
  Prettier), а правила архитектуры: границы слоёв, запрет импортов вбок, `type` вместо `interface`.

Node.js — только локальный инструмент. В продакшене рантайм Workers: нет процесса, диска и произвольных
Node-пакетов; совместимость проверяем для конкретной зависимости и `compatibility_date`.

## Раскладка

Модульный монолит, один Worker. Группируем **по фиче**, не по слою: фича = папка в `src/modules/`.
Добавить функционал — добавить папку, удалить — удалить папку. Пустые слои и папки заранее не создаём,
поэтому сейчас нет ни `modules/`, ни `core/`.

```text
src/
  index.ts              # composition root: собирает приложение, export default app
  app/                  # ВХОД в приложение. Не фича — удалить нельзя
    middleware/         # error.ts  logger.ts
  lib/                  # МЕЛКИЕ domain-agnostic утилиты
    errors.ts           # AppError: code + retryable. Про HTTP не знает
    logger.ts           # структурный лог одной строкой JSON
  types/  env.ts        # общие типы: биндинги и переменные контекста
```

**Вход и фичи разведены.** `app/` — это как приложение принимает работу: HTTP-роуты, доступ,
позже очередь и cron. Удалить это нельзя, фичей оно не является. `modules/` — только фичи: каждая
живёт своей папкой и не знает, кто её позвал. Сервисы не получают `Context` Hono — только обычные
данные и явные зависимости. DI-контейнер не нужен.

⚠️ **Данные фичи живут в самой фиче.** В `const/` попадает только то, что нужно и входу, и фичам
одновременно, а в `types/` — контракты между ними. Общие схемы валидации заводим в `src/schemas/`,
когда у схемы появляется вторая сторона; до этого она лежит рядом со своим единственным потребителем.

## Слои и направление зависимостей

Слои строгие: **импорт только вниз, и никогда вбок**.

```
src/index.ts              composition root — единственное место, где вход и фичи знают друг о друге
      │ собирает и связывает
      ├──────────────┐
      ▼              ▼
app/            modules/     друг друга НЕ видят ни в ту, ни в другую сторону
      └──────┬───────┘
             ▼
core/                        доменное ядро. Ни о входе, ни о фичах не знает
             ▼
lib/                         утилиты. Ни о домене, ни о фичах не знает
             ▼
types/ schemas/ const/       уровень 0: импортируются откуда угодно, сами не импортируют ничего
```

| Откуда      | Куда можно                           | Куда нельзя                                      |
| ----------- | ------------------------------------ | ------------------------------------------------ |
| `index.ts`  | всё                                  | —                                                |
| `app/*`     | `core`, `lib`, уровень 0, свои файлы | **`modules/*`**, `index.ts`                      |
| `modules/X` | `core`, `lib`, уровень 0, свои файлы | **`modules/Y`** (сосед), **`app/*`**, `index.ts` |
| `core`      | `lib`, уровень 0, свои файлы         | `modules/*`, `app/*`, `index.ts`                 |
| `lib`       | уровень 0, свои файлы                | `core`, `modules/*`, `app/*`, `index.ts`         |
| уровень 0   | ничего                               | всё остальное                                    |

Почему фича не видит вход: её должно быть можно поднять из очереди и cron, а не только из HTTP.
Почему вход не видит фичу: иначе `app` пришлось бы править при каждой новой фиче.

- **`lib/`** — мелкое, domain-agnostic и переиспользуемое. Ничего «сверху» не импортирует **и не
  реэкспортирует**: реэкспорт типа из `core` или модуля делает `lib` зависимым от домена окольным
  путём. Крупные доменные подсистемы сюда не кладём.
- **`core/`** — доменное ядро для нескольких фич: появляется, когда одно и то же нужно двум модулям.
  Наружу — самодостаточные функции, низкоуровневое внутри. Внешний клиент, нужный **нескольким**
  модулям, живёт здесь. Модули импортируют `core` напрямую — порты нужны только между модулями.
- **Клиент, нужный одному модулю, — `upstream.ts` рядом с его `service.ts`.** Внешний ответ
  проверяем схемой, маппинг в наш тип — внутри адаптера. ❌ Сырой контракт чужого API наружу не течёт.
- ❌ Циклы недопустимы. Внутри модуля импортируем конкретные файлы, а не собственный `index.ts`.

Проверяется механически — правилом `import/no-restricted-paths` в `eslint.config.mjs`. Зоны на слои
заданы явно, а зона «не импортируй соседа» **генерируется из списка папок `src/modules/`**: новый
модуль получает защиту сам, без правки конфига. Ловятся оба написания — и `src/modules/...`,
и обход через `../`, потому что путь резолвится, а не сравнивается как строка.
Ошибка видна прямо в редакторе, а не только на pre-push. На это есть тест — `scripts/tests/architecture.test.js`.

## Как модули работают друг с другом

`import { saveVersion } from 'src/modules/materials'` внутри другого модуля — **ошибка**, даже через
публичный `index.ts`. Иначе слой «модули» превращается в клубок, и удалить фичу удалением папки
перестаёт получаться.

Вместо этого модуль **объявляет порт — тип того, что ему нужно**, и получает зависимость аргументом:

```ts
// modules/<consumer>/service.ts — потребитель описывает СВОЙ минимальный контракт
type Deps = { saveVersion: (input: NewVersion) => Promise<VersionId> };

export const composeDraft = async (input: DraftInput, deps: Deps) => {
  /* ... */
};
```

```ts
// src/index.ts — composition root: единственное место, где фичи встречаются
const consumer = createConsumer({ saveVersion: materials.saveVersion });
```

Тип зависимости описывает **потребитель**, а не владелец: структурная типизация TypeScript сведёт их
в `index.ts` без единого импорта между модулями. Заодно сервис становится проверяемым без всей сборки.

Когда двум модулям нужно одно и то же, есть ровно три законных исхода:

1. **Общее опускается в `core/`** — если это доменная механика.
2. **Связь поднимается в оркестратор** — сценарий, который ходит в несколько модулей, живёт отдельной
   фичей и получает их порты аргументами. Обратных зависимостей на оркестратор нет ни у кого.
3. **Данные читаются через порт владельца** — чужие данные не трогаем: ни `queries.ts` соседа, ни его
   SQL. Нужна выборка со связью — её пишет **владелец** данных и отдаёт готовый тип.

У данных **один владелец**: хранилище описывается там же, где код, который им распоряжается.

## Устройство фичи

**Канон обязателен для `modules/`.** Открыв любую фичу, видишь одно и то же — угадывать не нужно.
Заводим только те роли, что реально нужны, — но **называем всегда так**:

`index.ts` публичный контракт (код писать можно) · `service.ts` логика, зависимости аргументами ·
`queries.ts` запросы к своим данным · `schema.ts` валидация внешних данных · `types.ts` типы фичи ·
`upstream.ts` внешний API только этой фичи

⚠️ **`core/` и `app/` этому канону НЕ подчиняются.** Это общая инфраструктура и вход — они не обязаны
иметь полный набор ролей. Хватает одного файла — пусть будет один файл; разрослась роль — она
становится папкой с тем же именем и `index.ts` внутри; папка с одним `index.ts` сворачивается обратно
в файл.

Правило одно: **лишних файлов нет нигде, обязательный канон — только в фичах.**

❌ `controller.ts` — это **набор функций, а не класс**: классовый контроллер ломает вывод типов в Hono.
❌ `utils.ts` как свалка: осмысленный кусок получает файл по имени (`rules.ts`, `retry.ts`).

**Где живут schema и types:** в модуле (`schema.ts`, `types.ts`) **ИЛИ**, если нужны ≥2 модулям,
в `src/schemas/` и `src/types/`. ❌ Не заводим их в `core/` и `lib/` — там логика.

## Платформенные лимиты (Free)

Проверено 19 сентября 2026 по [документации Cloudflare](https://developers.cloudflare.com/workers/platform/limits/).
Здесь только то, что действует на текущий воркер; квоты подключаемого сервиса проверяем в момент,
когда его подключаем.

| Лимит                         | Значение         | Что из этого следует                       |
| ----------------------------- | ---------------- | ------------------------------------------ |
| Workers Free: запросы         | 100 000/день     | потолок обращений ко всему приложению      |
| Workers Free: CPU             | **10 мс** каждый | ожидание сети не CPU; считать нужно разбор |
| Workers Free: **subrequests** | **50** на вызов  | бюджет внешних вызовов в одном обработчике |

- При исчерпании квоты функция **останавливается с уведомлением**; автоматического перехода на
  платный тариф нет.
- ❌ Переход на платный тариф Cloudflare или подключение платного сервиса — только с явного
  согласия владельца.

## Биндинги и env

Деплой **всегда с явным окружением** (`--env dev` / `--env production`). Верхний уровень — база,
напрямую не деплоится. dev и production — **разные** ресурсы.

Биндингов и секретов сейчас нет: они появляются вместе с функцией, которой нужны, а не «на будущее».
Когда будешь добавлять первый:

- ⚠️ **Биндинги окружениями не наследуются.** `main`, `compatibility_date`, `compatibility_flags`,
  `account_id` держатся один раз сверху, а `vars`, `d1_databases`, `kv_namespaces`, `r2_buckets`,
  `queues`, `durable_objects`, `triggers` дублируем в **каждый** env — иначе wrangler напишет
  «is not inherited by environments» и биндинга не будет.
- **После любой правки `wrangler.jsonc` → `pnpm cf-typegen`.** `worker-configuration.d.ts`
  генерируемый, руками не редактируем, в git не держим.
- Секрет — `wrangler secret put NAME --env <env>`, никогда не `vars`. Локально — `.dev.vars`
  (в `.gitignore`); заводя первый секрет, положи рядом `.dev.vars.example` с пустыми полями.

## Ошибки, секреты и логирование

- Единый `AppError { code, message, retryable }`. HTTP-статус из кода делает вход
  (`app/middleware/error.ts`), сама ошибка про транспорт не знает — её же будут кидать очередь и cron.
  ❌ Голый `throw new Error` наружу.
- Логи структурные, одной строкой JSON: request ID, путь, статус, длительность, код ошибки.
- ❌ Никогда не логируем и не отдаём наружу: токены, заголовки авторизации, подписанные URL,
  пользовательские данные, сырые тела внешних ответов.

## Конвенции

- **Только `type`, без `interface`.** Функции-хелперы — стрелочные (`export const fn = () => {}`).
- Внешние данные — сначала `unknown`, затем схема. Типы выводим из схемы, руками не дублируем.
  Обоснованный `any` — комментарием, почему.
- **Имена:** папки kebab-case; файлы внутри модуля — по роли (`service.ts`), без префикса фичи.
- **Порядок в файле:** типы → константы → экспортируемые функции → внутренние хелперы.
- **Импорты:** кросс-модульное — абсолютом от `src/` (`import { AppError } from 'src/lib/errors'`,
  alias `src/*` в `tsconfig.json`); сиблинги — относительным `./`.
- **Кроссплатформенность.** Код и скрипты работают и на macOS, и на Windows: в `package.json` только
  `node` и бинарники из `node_modules`, вспомогательные шаги — `scripts/*.js`, переносы строк LF.
- Зависимость добавляем под конкретную задачу. Пустые абстракции и «универсальные базовые сервисы»
  заранее не создаём.
- Тесты идут внутри workerd и входят в `pnpm check`. Покрываем инварианты, а не проценты —
  список в `docs/testing.md`.

## Как добавить фичу

Механически. Снаружи папки фичи трогаем ровно один файл.

1. **Папка фичи** `src/modules/<feature>/` — только нужные роли из канона выше.
2. **Связывание** — в `src/index.ts`: создать сервис и подключить его к входу. Если вход должен
   что-то знать о фиче, порт описывает **потребитель** — импортов между `app` и `modules` не появится.
3. **Проверить**: `pnpm check`.

❌ Чего делать не нужно: править вход при добавлении фичи, импортировать соседний модуль,
складывать данные фичи в `const/`, заводить пустые файлы «на будущее».

## Инварианты (Do / Don't)

- ✅ Логика в `service`, тонкий хендлер сверху. ❌ Бизнес-логика в роуте.
- ✅ Все ошибки через `AppError`. ❌ Сырой текст внешней ошибки пользователю.
- ✅ У каждого внешнего вызова таймаут. ❌ Повтор вслепую при неизвестном результате.
- ✅ Модули связываются только в `src/index.ts` через порты. ❌ Импорт соседнего модуля — даже его `index.ts`.
- ✅ `lib` ничего не знает о домене. ❌ Реэкспорт из `core`/`modules` внутри `lib`.
- ✅ Общее у двух модулей опускается в `core` или поднимается в оркестратор. ❌ «Просто импортну соседа».
- ✅ Состояние — во внешнем хранилище. ❌ Состояние в глобальной переменной изолята: он живёт минуты.
