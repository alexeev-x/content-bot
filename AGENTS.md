## Непереговорные правила

- **Модульный монолит, не микросервисы.** Поначалу один Worker, одна D1, одна Queue, один Cron. Реалистичный ориентир до 1 000 фоновых задач/сутки, всё без обязательных платных API.
- Каждый модуль отвечает только за одну бизнес-возможность. Внешний мир (Hono, D1, Telegram, R2, Queue) подключать через узкие порты в местах реальных зависимостей. Из других модулей импортировать только публичный `index.ts`, никаких deep imports, циклов и импортов infrastructure в domain.
- `app/container.ts` вручную связывает адаптеры, не использовать скрытый Service Locator.
- Никогда не сохранять состояние пользователя, запроса или задания в изменяемых module-level переменных. Размер ответов/файлов, batch и параллельность ограничены.
- **Безопасность публикаций:** очередь at-least-once; D1 владеет состоянием и дедупликацией; при возможном отправленном, но неподтверждённом запросе Telegram — `unknown` и ручная сверка, НЕ автоматический повтор.
- UI не содержит Telegram bot token или ключи API; все административные операции проходят серверную авторизацию и CSRF. Сервер перепроверяет Zod-схемы и полномочия независимо от клиентской валидации.
- Строго разделять server state (TanStack Query), form state (React Hook Form), URL state (роутер), локальный UI state. Не делать глобальный store по умолчанию. Мутабельные внешние эффекты очищать.
- Любая новая возможность: модель, публичный контракт при необходимости, реализация, обработка ошибок/пустоты, тесты и документация. **Не генерировать пустые архитектурные обёртки**.
- Не добавлять платные ИИ-провайдеры, рендер-API или облачные тарифы без прямого решения владельца.
- Не коммитить секреты, cookies, пароли, личные данные, исходные продакшен-ключи. Staging использует отдельного Telegram-бота/канал и БД.

## Предрелизный контроль

- `npm ci`, `typecheck`, `lint`, `test:architecture`, `test:unit`, `test:integration`, `build`.
- Backend: double Cron, duplicate Queue, Queue failure after D1 insert, unknown Telegram response, webhook duplicate, 429 retry, session/CSRF tests.
- Frontend: 401/403/409, dirty editor, preview matches renderer, no optimistic publish success, polling stops on hidden tab/unmount, mobile layout and keyboard navigation.
- При изменении SQL создавать миграцию. При удалении модуля остановить новые задания, завершить/отменить старые, отдельно удалять данные миграцией.
- Изменение контракта всегда сопровождается обновлением `packages/contracts`, фронтенда, backend и контрактных тестов.

## Definition of Done

Задача завершена только если код проходит CI, ошибки воспроизводимы и отображаются в админке, контракты не разъехались, тесты подтверждают критичные сценарии и документация отражает фактическую реализацию. При отсутствии измерений не заявлять, что система гарантированно выдерживает 1 000 задач/сутки — указывать, что это целевой ориентир до нагрузочного теста.

## Мультиагентная разработка — решение владельца 03.10.2026

Figma полностью исключена. Единственный управляющий — Orchestrator; специалисты: Product Analyst, Design System, Frontend, Backend, QA/Security. Каждый получает минимальный task packet, а не весь репозиторий и не весь чат. Оркестратор назначает задачи, отслеживает зависимости, запрашивает результат по контракту, запускает проверку и эскалирует решения владельцу. Дизайнер передаёт токены и кодовые UI-примитивы; frontend не ожидает Figma-макеты. Детальная спецификация: docs/AGENT_ORCHESTRATION.md, docs/DESIGN_SYSTEM_NO_FIGMA.md и agents/*.md.
