# Ловушки стека content-bot

Всё ниже проверено на этом проекте. Каждый пункт когда-то стоил времени — не наступай повторно.

## Telegram Bot API

| Что                                | Правда                                                                                  |
| ---------------------------------- | --------------------------------------------------------------------------------------- |
| Автор отправляет файл боту         | до **2 ГБ** (это делает клиент Telegram, не бот)                                        |
| Бот **скачивает** файл (`getFile`) | **20 МБ**, жёстко. Локальный Bot API server снимает лимит, но на Workers его не поднять |
| Бот отправляет новый файл          | 50 МБ                                                                                   |
| Бот **пересылает по `file_id`**    | без ограничений                                                                         |

- **Списка тем приватного чата API не отдаёт.** Поэтому база — единственный источник правды
  о разделах, а `ensure` идемпотентен только относительно неё. Потеряли базу при живом чате —
  получите дубли, и почистить их можно лишь по сохранённым `thread_id`.
- **События об удалении темы нет.** Есть created/edited/closed/reopened, deleted — нет. Узнать
  можно только попыткой записи: придёт `message thread not found`.
- **Скоупа команд на тему не существует.** У `setMyCommands` семь scope (чат, участник, админы…),
  темы среди них нет. Разграничение команд по разделам — наша логика во входе.
- **Темы в приватном чате** включаются в @BotFather → Mini App → Bot Settings → **Threads Settings**
  → Threaded Mode. Второй переключатель запрещает пользователю создавать и удалять темы — он включён.
- **Иконка темы — только 6 цветов** (`iconColor` в `core/telegram.ts`), либо кастомное эмодзи.
- Явные отказы Telegram (`400`, `403`) автоматически не повторяем. `429` сохраняет `retry_after`.
  Сеть, таймаут и `5xx` у отправки/создания темы дают неизвестный исход: сверка по `docs/recovery.md`.

## grammY

- **`botInfo` обязателен до обработки апдейта.** Без него grammY зовёт `getMe` — лишний запрос
  в Telegram на КАЖДЫЙ апдейт и трата лимита subrequests. Берём из `BOT_INFO`, иначе кэшируем
  на изолят.
- **`webhookCallback` по умолчанию сдаётся через 10 секунд.** Для холодного старта мало: первые
  апдейты падали. У нас 50 с — ниже порога, после которого Telegram считает доставку неудачной.
- **Webhook обязан пробрасывать ошибку.** `bot.catch` обслуживает long polling; в webhook-режиме
  вход разворачивает `BotError` и передаёт исходный `AppError` общему обработчику Hono.
- **grammY живёт только в `app/telegram`** и только для разбора апдейта и маршрутизации. Вся
  отправка — через `core/telegram`, иначе тот же код не получится вызвать из очереди и cron.
- Тип контекста сужай (`Filter<Context, 'message:text'>`) вместо `ctx.chat?.id ?? 0`.

## Hono

- Значения контекста типизируются через `Variables` в `AppEnv` — каст `as never` не нужен.
- `onError` — единственное место, где код ошибки превращается в HTTP-статус. `AppError`
  про транспорт не знает.

## Drizzle + D1

- **Миграции генерируются, а не пишутся**: схема в `table.ts`, затем `pnpm db:generate`.
- ⚠️ **Glob в `drizzle.config.ts` — `./src/**/table.ts`.** Таблицы есть не только у фич: дедуп
  апдейтов живёт во входе. Сузишь glob — генератор молча выдаст `DROP TABLE`.
- **Дедуп через состояние**: конфликт ключа ещё не означает завершение. `done` подтверждаем,
  активную аренду не захватываем, просроченную можно захватить условным `UPDATE`.
- **`.returning()` может вернуть пусто** — с `noUncheckedIndexedAccess` это ловится типами, проверяй.
- **Интерактивных транзакций в D1 нет.** Атомарность — `batch` или один `UPDATE` с условием.
- **Внешний вызов и запись в базу — не одна транзакция.** Между ними возможен сбой.

## Cloudflare Workers

- ⚠️ **Шесть одновременных соединений**, ожидающих заголовки ответа. Пачка параллельных вызовов
  к внешнему API упрётся в это раньше, чем в лимит subrequests.
- **128 МБ памяти на изолят** — ещё одна причина не читать файлы целиком.
- **Глобальные переменные — не память.** Изолят живёт минуты. В глобалах только кэш, потеря
  которого ничего не ломает (`botInfo`). Состояние разделов читаем из D1.
- **50 subrequests на вызов**, **10 мс CPU** на Free (ожидание сети не считается).
- **У каждого `fetch` таймаут.** Без него зависший вызов держит обработчик до таймаута webhook.
- Биндинги живут в `env` конкретного вызова — зависимости собираются на запрос, не при импорте.
- Типы биндингов генерируются для окружения: `wrangler types --env dev`. Без `--env` биндинги,
  объявленные внутри env, станут опциональными.

## Локальная разработка

- **Telegram не достучится до localhost.** `pnpm dev` сам забирает апдейты (`getUpdates`,
  long polling) и отдаёт их воркеру тем же запросом, что прислал бы Telegram.
- **`getUpdates` пускает одного читателя.** Второй `pnpm dev` или `pnpm bot --whoami` оборвёт
  опрос. У long poll обязан быть таймаут, иначе после обрыва он зависнет навсегда.
- **Сломанный IPv6 в локальной сети** даёт ровно эту картину: первый вызов Bot API висит 15 секунд,
  повтор проходит мгновенно. Node и curl это переживают (Happy Eyeballs), workerd — нет.
  Проверка и лечение — в `docs/setup.md`.

## Тесты

- Для модульных тестов передавай транспорт аргументом — `createHttpClient(url, { fetch })`.
  Интеграционные тесты используют общий перехват Telegram; любой другой внешний запрос запрещён.
- В текущем плагине D1 между тестами файла не очищается автоматически: это делает `tests/setup.ts`.

## Как здесь диагностировать

1. **Сначала факты, потом гипотезы.** В этом проекте пять правдоподобных версий подряд оказались
   ложными, а виноват был IPv6. Каждая проверка стоила минут, каждая гипотеза — часа.
2. **Логи локального воркера читаются запросом**, их не нужно просить у пользователя:

   ```bash
   curl -s -X POST http://127.0.0.1:8787/cdn-cgi/local/explorer/api/local/observability/query \
     -H 'Content-Type: application/json' \
     -d '{"sql":"SELECT message FROM logs ORDER BY rowid DESC LIMIT 20"}'
   ```

   Таблицы: `logs` и `spans` (у `spans` есть `duration_ms` — сразу видно, что висит).

3. **Убедись, что твоя проверка действительно проверяет.** Дважды здесь «зелёный» результат
   означал, что команда не существует или упала иначе: `pnpm lint` был удалён, а `grep error`
   не ловил краш ESLint. Проверяй на заведомо ломающем примере.
4. **Не трогай процессы пользователя.** `pkill -f wrangler` убьёт его `pnpm dev`; порт 8787
   может быть занят им. Для своих проверок бери `--port 8788`.
