# Ловушки стека content-bot

Всё ниже проверено на этом проекте. Каждый пункт когда-то стоил времени — не наступай повторно.

## Hono

- Значения контекста типизируются через `Variables` в `AppEnv` — каст `as never` не нужен.
- `onError` — единственное место, где код ошибки превращается в HTTP-статус. `AppError`
  про транспорт не знает: его же будут кидать очередь и cron.
- Роутов сейчас нет, поэтому любой путь отвечает 404. Это ожидаемое состояние, а не поломка.

## Cloudflare Workers

- ⚠️ **Шесть одновременных соединений**, ожидающих заголовки ответа. Пачка параллельных вызовов
  к внешнему API упрётся в это раньше, чем в лимит subrequests.
- **128 МБ памяти на изолят** — причина не читать файлы целиком.
- **Глобальные переменные — не память.** Изолят живёт минуты. В глобалах только кэш, потеря
  которого ничего не ломает.
- **50 subrequests на вызов**, **10 мс CPU** на Free (ожидание сети не считается).
- **У каждого `fetch` таймаут.** Без него зависший вызов держит обработчик до общего таймаута.
- Биндинги живут в `env` конкретного вызова — зависимости собираются на запрос, не при импорте.
- Типы биндингов генерируются для окружения: `wrangler types --env dev`. Без `--env` биндинги,
  объявленные внутри env, станут опциональными.
- ⚠️ **Биндинги не наследуются окружениями.** Всё, что объявлено сверху (`vars`, `d1_databases`,
  `kv_namespaces`, `r2_buckets`, `queues`, `durable_objects`, `triggers`), нужно продублировать
  в каждый `env`, иначе wrangler напишет «is not inherited by environments».

## Локальная разработка

- `wrangler dev` поднимает воркер локально: ни логина в Cloudflare, ни публичного адреса не нужно.
- **Сломанный IPv6 в локальной сети** даёт очень узнаваемую картину: первый вызов внешнего API
  висит 15 секунд, повтор проходит мгновенно. Node и curl это переживают (Happy Eyeballs),
  workerd — нет. Проверка и лечение — в `docs/setup.md`.

## Тесты

- Для модульных тестов передавай транспорт аргументом, а не подменяй глобально.
- Единственная глобальная подмена — запрет сети в `tests/setup.ts`. Прогон подхватывает настоящий
  `.dev.vars`, поэтому исходящий запрос должен падать, а не уходить наружу.

## Как здесь диагностировать

1. **Сначала факты, потом гипотезы.** В этом проекте пять правдоподобных версий подряд оказались
   ложными, а виноват был IPv6. Каждая проверка стоила минут, каждая гипотеза — часа.
2. **Логи локального воркера читаются запросом**, их не нужно просить у пользователя:

   ```bash
   curl -s -X POST http://127.0.0.1:8787/cdn-cgi/local/explorer/api/local/observability/query \
     -H 'Content-Type: application/json' \
     -d '{"sql":"SELECT message FROM logs ORDER BY rowid DESC LIMIT 20"}'
   ```

   Таблицы: `logs` и `spans` (у `spans` есть `duration_ms` — сразу видно, что висит).

3. **Убедись, что твоя проверка действительно проверяет.** Дважды здесь «зелёный» результат
   означал, что команда не существует или упала иначе: `pnpm lint` был удалён, а `grep error`
   не ловил краш ESLint. Проверяй на заведомо ломающем примере.
4. **Не трогай процессы пользователя.** `pkill -f wrangler` убьёт его `pnpm dev`; порт 8787
   может быть занят им. Для своих проверок бери `--port 8788`.
